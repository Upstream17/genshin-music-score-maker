## 0.5 ⭐⭐ 交付前的五条硬验收（2026-10-15 加，踩过两次「跑调」后定的；2026-10-17 补第⑤条）

**这两次事故的形态一样：脚本全绿（强校验 0ms、丢音 0、21 键合法），但用户一听就说「跑调 / 乱按」。**
因为**「忠实于源 MIDI」证明不了「旋律还成形」**。所以任何成品的自检报告里必须包含这五条，缺一条不许交付：

| 指标 | 怎么算 | 合格线 |
|---|---|---|
| ① **八度跳占比** | 成品按下事件按时间排序，取相邻音程；同句内（间隔 <900ms）的 `abs(Δ)>=12` 占比 | **≤2%**（>5% 必然「乱按」）|
| ② **折叠数** | `convert` 返回的 `st["folded"]` | **0** |
| ③ **长空档** | 相邻按下间隔 >2s 的处数与位置 | 逐处确认是**原曲乐句停顿**，不是抽样断了 |
| ④ **前 30 个按下音** | 直接打出来，肉眼核对该曲主题 | 能认出该曲开头 |
| ⑤ **时长中位数** | 成品按下事件的 `end-start` 排序取中位 | **≥150ms**；若中位≈30ms 就是「时长当结束时刻」的 bug |

- ⭐⭐ **⑤ 是 2026-10-17 稻香事故加的**：写构建脚本时把「**时值**」当成「**结束时刻**」存进元组
  （`notes.append((s, min(d, DUR), ...))` 而后面按 `s+dur` 用），下一步 `max(e, s+0.030)` 就把**每个音都算成 30ms 点击音**。
  用户听感是「高音被截断了 / 跑调」，但 `verify_delivery.py` **不查时长**（当时 9 PASS 全绿），强校验也是 0ms。
  **自检加一行即可**：`durs=sorted(round((b-a)*1000) for a,b,_ in events); print(durs[len(durs)//2])`。
  同一次事故还叠了第二个坑：**给旋律/伴奏设「硬性时长上限」**（如旋律 1.20s、伴奏 0.90s）会把
  乐句尾的 1.46s 长音削掉 → 用户听成「每句结尾的高音断了」。**通用原则：除非有理由，别设上限**，
  同键让位交给 §4c 的 35ms 规则去处理。

- ⭐⭐ **① 是这次唯一能提前抓住「跑调」的指标**。做法：`on=sorted((按下ms, 音高))`，算相邻音程，
  数 `abs(Δ)>=12` 的比例。实测翻车版：茉莉花 **45%**、梁祝前 40 音是 `G3 A3 A3 A3…` 的颤音。
- ⭐⭐ **零折叠的正确做法：用「音高集合」搜移调，不要用固定移调。**
  取旋律的**去重音高集合**（通常只有 10 来个音），在琴域 48–83 内扫 `tr`，挑 `min+tr>=48 且 max+tr<=83` 的那些值，
  再在候选里按「黑键最少」选。**同一音高集合会有多个合法移调（相差 12 的倍数），要挑对同余类** ——
  实测茉莉花：正确是 `+2`（D3–B4）或 `+14`（C4–A5），而我错用了 `+7`（G3–E5），
  有音超出下界 → `convert` 又折回来 → 10 处八度跳。**`+7` 根本不在合法候选里。**
- ⭐⭐ **别把 MIDI 里的「同曲调副本轨」合并**。总谱里同一旋律常被复制到 2–4 条轨（不同八度/不同乐器），
  它们是**分声部**，不是同一个声部：合并后再按各自音区折带 → 同一条旋律被拆到两排 → 相邻音永远在跳八度。
  **正确做法：只取一条轨（选音符最多、最连续、单音音头比例最高的那条），整条放进一个不用折的音区。**
- ⭐⭐ **总谱类 MIDI 的旋律常常「分段分散在多轨」**（梁祝实测：轨3 有 19→96s 的 77 秒空白、
  轨4 有 60→140s 的 80 秒空白，两者互补但仍有洞）。**动手前先画时间覆盖表**：
  逐轨列出「每 20s 有几个音、最长连续段多长、有多少 >1.5s 空档」，**确认存在一段连续且单声部的旋律**再开工。
  若所有轨都是断续片段 → **如实告诉用户「这份源里没有完整旋律」，不要硬拼**。
- ⭐ **`press_intervals` 返回的键是「键字母」，`KEYMAP` 是「音高→字母」**：
  `REV={v:k for k,v in KEYMAP.items()}` 会**因为字母重复而只剩 9 条**（我踩了三次）。
  要字母→音高就写 `K2P` 并把 `KEYMAP` 反过来建，或直接用 `[v for s,e,v in intervals]` 拿音高。

## 0.6 ⭐⭐⭐ 多轨 MIDI 的「织体还原」完整流程（2026-10-15 加，茉莉花迭代收敛后定稿）

**这一轮来回十几版的根因只有一个：我把「验证一个音对不对」当成了「验证整首对不对」。**
成品全绿（折叠 0、吸附 0、丢音 0、强校验 0.00ms），用户却一路指出五个不同的问题，
每一个都不是"音错了"，而是**"结构错了"**。以下每条都是被用户实际指出来后验证的。

### ① **先画时间覆盖表，再看总音数统计**（最重要，防"中间大段空白"）
用户原话：「中间有大段空白的主旋律，只有和弦的部分，怎么回事」。

**别只看 `len(track)` / 首音时刻 / 末音时刻** —— 312 个音摊在 171 秒里看着很连续，实际断成四截。
必做：
```python
for ti in sorted(set(t[3] for t in notes)):
    b = collections.Counter(int(t[0]//10)*10 for t in notes if t[3]==ti)
    print(ti, [b.get(i*10,0) for i in range(n_buckets)])       # 每 10s 一个数
    ons = sorted(set(t[0] for t in notes if t[3]==ti))
    print([(ons[i], ons[i+1]-ons[i]) for i in range(len(ons)-1) if ons[i+1]-ons[i] > 1.5])   # >1.5s 空档
```
实测：轨1 有 3 段空档 **41.6–53.7s / 77.5–114.7s / 138.4–152.3s（最长 37.2 秒）**，
而轨2 竖琴全程 805 音都有 —— 于是成品里那 69 秒就"只有和弦"。

### ② ⭐⭐ **主旋律可能由「两条互补的轨」拼成 —— 空档处的答案是「另一条轨接着弹」**
实测：**轨1 在四段有音、轨6 正好在三段空档里接着弹**（长间隔仅 0.9–1.8s），两轨同音高、只差一个八度。
判定方法：取轨A 的每段空档 `[a,b)`，数**其他轨**在该区间的音数/最长间隔：
```python
for a,b in gaps:
    for ti in others:
        seg = [t for t in notes if t[3]==ti and a<=t[0]<b]
        if seg: print(ti, len(seg), max 间隔)
```
合并前**必须按八度对齐**（轨6 比轨1 高 12 半音 → `p-12`），否则旋律会在两个八度间跳。
合并后实测：最大空档 **37.2s → 4s**。这是把"只有和弦的部分"救回来的唯一办法。

### ③ ⭐⭐⭐ **绝对不要「按排分音区」—— 那是在改音程关系，必然跑调**
用户原话：「不是说主旋律高音、和弦低音压在一层，**音调不按层来的**」「压在一层还跑调」。
- 错误做法：旋律整条折进高排（72–83）、和弦整条折进中排（60–71）→
  和弦的音被搬动了 12 的倍数 → **和弦与旋律的音程关系被破坏** → 听起来"跑调"。
- 正确做法：**所有层用同一个移调量，每个音按自身音高落在哪一排就是哪一排**。
  结果自然就是"和弦相对低、主旋律相对高"，而且是**原谱的真实关系**。
- ⭐ 顺手检查：**别空出一整排**。若三排只用了两排，说明移调选窄了 ——
  实测成品按键应达 **18–20/21**、低/中/高三排都有音符。

### ④ ⭐⭐ **"主旋律必须完整"决定了移调量的可行区间**（先算这个，再挑别的）
用户原话：「主旋律丢失了几个高音，**需要把主旋律完整保留比较好**」。
设旋律原域 `[lo, hi]`，琴域 48–83 → 要一个音都不丢，`tr` 必须满足
`lo+tr >= 48` **且** `hi+tr <= 83`，即 `tr >= 48-lo` 且 `tr <= 83-hi`。
实测茉莉花（合并后旋律 **G#3–F6，跨 33 半音**）→ 只有 `tr <= -6` 才完整；
`-1` 会丢掉 52 个旋律音（就是用户听到的高音丢失）。**把候选按 `tr` 列出来，只保留"完整"那一列。**

### ⑤ ⭐ **琴只有 36 个半音，乐队总谱跨度常是 47 —— 超出就丢音，不要折叠**
实测：旋律跨 33、竖琴跨 47（F#2–F6），两轨合起来 **47 个半音**，琴域只有 `83-48+1 = 36`。
选 `tr` 时按这个顺序挑（三个指标同时看，不要只看一个）：
```
合计保留音数  >  旋律是否完整（硬条件）  >  黑键数（吸附量）
```
实测 `-6`：旋律 **489/489 完整**、竖琴 711/805、合计 **1200/1294 = 93%**（三个候选中最高）→ 选它。
**丢音（超域直接丢弃）是可接受的，折叠（改音高）不可接受。**

### ⑥ ⭐⭐ **分段移调：纯伴奏段可以单独用「零黑键」的移调量，更干净**
用户原话：「你其实可以最开始在主旋律进来前的琶音都保留的，**只有主旋律进来后才降调**」。
实测开头段（旋律未进的 65 个琶音音）：
| 移调 | 音域 | 黑键数 | 听感 |
|---|---|---|---|
| `+0` | G#3–D#6 | **54/65** | 更卡（大量吸附） |
| **`-1`** | G3–D6 | **0/65** | ✓ 圆润（65 音一个不丢） |
| `-6` | D3–A5 | 6/65 | F#4 被吸附 → 用户听到的"卡" |
做法：以**主旋律首次进入的时刻**为界，前面纯伴奏段单独选移调（优先"整段无黑键"），
后面整体用 ④ 定出的移调量。分界点落在乐句起点上就听不出突兀。

### ⑦ ⭐ **开头空白必须裁**：把源首音时刻平移到 `0.30s` 起。
用户原话：「最前面有一段空白，需要去掉」「开头旋律都错」。成品首音应为 300ms 左右。

### ⑧ ⭐ **同一移调量下，也会出现同键重击 <30ms** —— 交付前必查
实测：旋律+琶音合并后出现 **29ms**（差 1ms 触发 §4c 游标陷阱）。修法同 §4c：
按 key 分组，缩短前音尾巴留 `GAP=35ms`，注意**按下时刻不动**，然后**重新验证一遍**（应得 32ms）。

### ⑨ ⭐ **"按简谱手抄"极易错位 —— 把音高和节奏写成同一个元组**
我在按简谱生成时连续踩了 4 次：音级串与拍数数组长度不一致（85 vs 86、10 vs 9 …）。
**根治：不要维护两个平行数组**，写成 `(音级, 八度, 拍数)` 三元组，
或 `rhythm` 长度不足/超出时自动补齐/截断并 `assert len(L)==len(rh)`。
**更根本的教训**：当权威谱与源 MIDI 冲突时，先用**用户耳朵**定案 ——
用户说「前面的旋律是 E E G A C C A G G A G」后，任何与此不符的推理都是错的。

### ⑩ ⭐ **交付前最终自检脚本（照抄即可）**
```python
piv = m2.press_intervals(m2.decode_events(notes_str))
on  = sorted((a, b, L2P[k]) for k, l in piv.items() for a, b in l)
seq = [p for _, _, p in on]
print("音数", len(on), "时长", max(b for _,b,_ in on)/1000)
print("首音", min(a for a,_,_ in on), "ms")                  # 应 ≈300
print("音区 低/中/高", sum(p<60 for p in seq), sum(60<=p<72 for p in seq), sum(p>=72 for p in seq))
print("按键数", len(piv), "".join(sorted(piv)))              # 应 18–20/21
b = collections.Counter(int(a//10000)*10 for a,_,_ in on)
print("每10s音符数", [b.get(i*10,0) for i in range(19)])      # 不应有 0
print(">2s 空档", [(on[i][0], on[i+1][0]-on[i][0]) for i in range(len(on)-1) if on[i+1][0]-on[i][0]>2000])
print("同键最小间隔", min(s[i+1][0]-s[i][1] for k,l in piv.items() for s in [sorted(l)] for i in range(len(s)-1)))
```
→ 已固化为 **`scripts/verify_delivery.py`**（一条命令出 11 项指标 + PASS/WARN/FAIL，有 FAIL 退出码 1）。

### ⑪ ⭐⭐ **指标要按「编曲层数」重新定标 —— 别用单旋律的阈值卡多层编曲**
实测教训：拿 §0.5 的「八度跳 ≤2%」去验**用户已认可的**茉莉花多层版，报 **57.3% FAIL** —— 假警报。
原因：那版有**竖琴琶音层**，琶音本就跨两个八度，相邻音经常差 ≥12 半音。
- **单声部旋律**：`≥12 半音` 占比 **≤2%**（§0.5① 就是靠这个抓到 45% 的折叠翻车）。
- **多层编曲**（旋律+琶音/伴奏）：天然 **40–60%** 正常，`>85%` 或听着"跨排乱跳"才可疑。
所以 `verify_delivery.py` 分两档：默认多层阈值，加 `--mono` 收紧。
**教训：任何阈值在跨场景复用前，先用"已知正确样本"回归一遍，确认不误报。**
（同理：`>2s 空档` 判定必须结合"每 10s 音符数"看 —— 前者说"有洞"，后者说"洞在哪、多长"。）

### 1.2 找某一首特定的歌（免费库命中率极低，别抱幻想）
**免费库对「西方/日本」命中率高、对「华语流行」命中率极低** —— 华语 MIDI 基本是付费市场。
实测《香水有毒》在 BitMidi、光遇 Sky1984 合集(16,122 份)、`andy-yangz/midi_lyric_corpus`(250 首中文歌)、
WindSong 原神 MIDI 集里**全部没有**；有的站全带墙：midishow（积分）、虫虫钢琴（付费）、mymusic5（付费）、爱给网（免费但要登录）。
- **别在这些站上耗时间写抓取**：midishow / 虫虫 / MuseScore 全是 Cloudflare「Just a moment...」，自动化必败。
- **查一个库是否含某歌的正确姿势**（比 GitHub API 可靠 —— API 因共享 IP 会被 429 限流）：
  ```
  git clone --depth 1 --filter=blob:none --no-checkout <repo>
  git -c core.quotepath=false ls-tree -r HEAD --name-only   # ⚠ 必须加 quotepath=false，否则中文名是八进制转义、grep 不到
  ```
  （jsDelivr 的 `data.jsdelivr.com/v1/packages/gh/...` 对大库返回 403，小库可用。）
- **付费源不代下** —— 绕付费墙的脚本（如 chongchong-free）不做。正路：**让用户用自己的账号下**，我们负责转换。
- ⭐⭐ **先翻用户本地的 MIDI 素材库**（本机 `E:\BaiduNetdiskDownload\40万MIDI素材`，40 万首、按分类目录）：
  `find <库根> -iname "*<曲名>*"` 常能翻出**同一首歌的好几份不同编曲**，其中往往有一份**全曲版**
  （时长接近原曲、`parse_smf()["tempos"]` 正好 = 原曲 BPM）。这一份同时给出**权威 tempo + 段落结构 +
  前奏长度 + 真贝斯线**，比任何网上的谱都可靠，而且不用下载、不用过墙。
  → **处理任何一首歌之前，先在这里搜一次**（几秒钟），再决定要不要去网上找。
- 用户从 midishow 下到 `.mid` 后 → 走 §4(b2)。
- ⭐ **查「这首歌的调性结构 + 音域」，别去翻谱**：搜「<曲名> 二胡/古筝/合唱 怎么拉 / 几个调 / 音域」。
  器乐翻奏要换指法时，作者一定会把转调讲清楚，顺带给音域度数 —— 这是拿到「调号 + 转调 + 音域」三项最省力的路径。
  （实测《九儿》：一篇文章同时给出「要换三种调」和「音域从十度提高到十二度」。）
- 华语流行在免费库里缺失是**常态**，别因为「这么有名的歌应该有吧」而多试几个库：《九儿》在 Sky1984 全量 16,122 份、
  `midi_lyric_corpus` 250 首里都没有。查 2–3 个主库没有 → 立刻换路径（要用户给 MIDI / 扒谱 / 改编），别继续搜。

### 1.3 mp3 扒谱（兜底路线，别承诺「一键支持所有曲子」）
**链路**：`mp3 → demucs 分离人声 → basic-pitch 扒 → 单声部化 → 量化 → 折进 C 大调` → 接 §4(b)。
工具三层：① 开源本地（可批量）= `basic-pitch`(Spotify) + `demucs`(Meta，流行歌必做前置) + `MT3`(Magenta，精度更高)
+ `hFT-Transformer`(Sony)/`piano_transcription`(ByteDance，纯钢琴最准)；② 在线 AI = Songscription / Klangio /
Melody Scanner / Pianolyze（更准但收费、不能批量）、免费网页 basicpitch.spotify.com；③ 人工扒谱。
**四道坑**：① 多声部（整曲直接扒 = 几十音同响）；② 转音/颤音被扒成乱音；③ ⭐**调性**（几乎不可能是 C 大调 →
只能吸附 → 音高被改，最致命）；④ 节奏量化。
**优先级**：先找现成 MIDI/光遇谱，扒谱是兜底。环境坑：torch/basic-pitch 要 **Python 3.11/3.12**（3.14 无轮子）。

### 1.4 ⭐ 接活第一件事：先判「这首歌能不能上琴」——两道闸
用户问「某首歌能弹吗 / 我想加这首」时，**先过闸再找谱**，别先埋头搜 MIDI。

| 闸 | 琴的硬限制 | 怎么判 |
|---|---|---|
| ① 音域 | **36 个半音**（C3–B5） | 流行歌通常 1–2 个八度（十度～十二度 ≈ 16–19 个半音）→ **几乎从来不是真障碍** |
| ② **调性** | **固定音高，只有 C 调 7 个白键** | 全曲用音级必须 ≤ 7 且能整体移进这个集合 → **中途转调的歌 = 原样弹不了**（最常见的真障碍） |

- ⭐ **判「移调多少」别靠肉眼读直方图，跑一张扫描表**：对偏移 −6…+6 各算一次
  「黑键音占比 / 八度折叠后落在 21 键上的可演奏率 / 折叠数」，打印成表：
  - **黑键 0%、可演奏率 100%** 的那一行 = 该曲音级正好是**一套大小调音阶的 7 个音** →
    **整首移到那一行就是无损的**（音程一个不差），同余类里再挑八度（±12）让音区落进 48–83。别用 `snap`。
  - **所有行都有黑键** = 曲子真用了变化音（或中途转调）→ 只能 `snap`（改音高，每吸附一个 = 一个错音）
    或按段改编（§8.4）。此时**取黑键最少的那一行当调性**，并**如实报残余吸附数** ——
    实测《传奇》E 大调 −4 后仍有 5.4%（51 个）变化音要就近吸附，对外别写成「无损」。
    同一同余类的两个八度（如 −4 与 +8）**音高内容完全相同**，差别只是哪一端要折：
    比两版的折叠数与低音键数（实测 −4 折 82 个低音但低音区用满 7/7；+8 只折 4 个高音但低音区空着）→ 两版都渲 mp3 让用户挑。
  - 扫描比直方图快且结论硬：黑键占比是**客观证明**，不是「听着像什么调」。对外汇报时给「原样黑键 X%、
    可演奏率 Y% → 移调后 Z%」，用户才知道你为什么动了他的调。
- 判调性还有两件要查：**调号** + **有没有转调**。证据来源与判据见 §1.2 与
  `references/modulated-song-arrangement.md`。
- **用户的猜测常常指错方向**（他担心音域，真障碍是转调）→ **先量再答，并明确说出他猜错了哪一点**，
  再把能做什么（三条改编路线 A/B/C）摆出来让他选。
- 别把「音域太宽」当成默认结论：先把度数算出来再答（琴的 36 半音摆在那里，一句话就能比）。

## 2. BetterGI 只认三种格式（`MusicScoreParser.cs`）
只认 `.json` / `.mid` / `.midi`；JSON 根必须是对象且含 `notes`。

| type | notes 语法 | 关键点 |
|---|---|---|
| `yuanqin`（缺省） | 带时值标记的字符串/数组 | `%`调速、`^`/`&` 显式按抬、`n.$` 连音、`#` 装饰音 |
| `midi` | `D<键><Δticks>\|U<键><Δticks>\|…` | Δ 都是**相对上一事件的非负增量**；时长(ms)=`Δticks*60000/(bpm*ticks)` |
| `keyboard` | 字母=按键、`-`=+1拍时长、`(…)`=和弦、`[…]`=琶音、`0`/空格=休止 | 预处理把 `/(`→`{`、`>` 去掉；`-` **每次只加 1 拍**，无法直接表示 1/2 拍 |

被静默过滤的细节：
- 合法按键只有 21 个 `QWERTYUASDFGHJZXCVBNM`（`SupportedKeys`），其它字母直接丢。
- `bpm` 写成字符串（`"120"`）也合法（Newtonsoft 会转），官方曲谱里就有。
- 相邻同键会触发 **30ms 提前松开**（`ApplyRepeatedKeyGap` / `Normalize`，`LowestLatencyMilliseconds=30`），刻意设计，不是 bug。

## 3. 「超出音韵、MIDI 播不出来」的真正原因 ⭐
21 键映射表（`InstrumentProfileService.StandardMappings`，风物之诗琴）：
```
Z=48 X=50 C=52 V=53 B=55 N=57 M=59 / A=60 S=62 D=64 F=65 G=67 H=69 J=71 / Q=72 W=74 E=76 R=77 T=79 Y=81 U=83
```
**纯 C 大调、无半音键、音域 48–83。** `BuildMidiTimeline` 调 `TryGetKey(note+transpose)`，
而 `TryGetKey` 在 `MelodicOctaveFold` 模式下**只做 ±12 八度折叠、从不吸附半音** → 折叠后查不到表就 `continue` **静默丢音**。
→ **凡带升号（C#/D#/F#/G#/A#）的音符 100% 丢失**；音域超界虽会折叠，折叠后落到升号上照样丢。
实测 80 首流行 MIDI 里 48 首在丢音，最惨的一首只剩 8.5% 可演奏。
排查：复刻 `TryGetKey`（八度折叠 + 查表）先算每首「可演奏率」，再决定要不要转。

### 3.1 ⭐ 用户问「能不能映射到别的乐器」（吉他 / 尤克里里 / 鼓 / 圆号）
先分清**两类乐器**，再谈可行性 —— 差别不在音色，在**键位**：

| 类 | 键位 | 后果 |
|---|---|---|
| **三排音符类**（风物之诗琴 / 老旧的诗琴 / 镜花之琴 / 钢琴 / 三排吉他） | 低排 `Z X C V B N M` = C3–B3、中排 `A S D F G H J` = C4–B4、上排 `Q W E R T Y U` = C5–B5，**与原琴 21 键完全同构** | 谱**原样可用**，不用改 |
| **上排是和弦的乐器**（上排 7 个按钮写着 `C Dm Em F G Am G7`，下面两排才是 do-re-mi） | 上排 = 7 个**和弦按钮**（**固定 C 大调、不可移调**），音符只剩 **2 个八度**（A–J 中音 + Z–M 低音） | ① 旋律丢掉高音那个八度；② 只能用那 7 个和弦 |

- ⚠⚠ **BetterGI 的 10 种内置乐器模板用的是同一套映射**（`InstrumentProfileService.cs`：风物之诗琴 / 老旧的诗琴 /
  镜花之琴 / 谐律键琴 / 跃律琴 / 悠可琴 / 晚风圆号 / 余音 / 绮筵之鼓 / 聚聚鼓 → 全部 `StandardMappings` = `Z=48 … U=83`，
  只有鼓类用 `Exact`）。所以在「上排是和弦」的乐器上放一份**用了 Q–U 的谱**，BetterGI 会**真的去按和弦按钮** ✗
  → 给这类乐器做谱，音高只能落在 **48–71**（A–J + Z–M 两排）。
- ⚠ **和弦类乐器 = 7 个固定和弦 + 2 个八度**：把曲子移到 C 大调 / A 小调后列出全部和弦，看有几个不在
  `{C, Dm, Em, F, G, Am, G7}` 里。有 2–3 个（尤其需要 **II / III / V 的大三和弦**时，表里只有对应的**小三和弦**）
  → **直接说「不建议映射到那个乐器，还是做 21 键原琴版」**，并把三条理由摆出来：少一个八度 / 和弦表固定 C 大调
  / 分解织体本来就装不下。
- ⭐ **「还原吉他韵律」不需要和弦按钮**：指弹分解和弦的本质就是**一个个音顺序弹出来** —— 21 键原琴逐音弹就是那个效果
  （和弦按钮一下出整组音，反而不像指弹）。用户真正想要的是这个，说清他就不纠结乐器了。
- ⚠ 别把「上排改了音」当成 bug 或调音问题：那是**乐器本身的键位设计**（上排从音符换成了和弦），
  先把它讲清楚再谈可行性。

## 4. 转换配方

### (a) `.txt` 键谱 → `type:"midi"` JSON（无损）
源格式（`GenshinAutoPlayLyre/lib.h` 的 `play()`）：第 1 行数字 `part`=1 拍秒数；字母连写=和弦；
`+` 累加 `part`、`-` 累加 `part/2`、`=` 累加 `part/4`；遇下一个字母才触发上一组。
做法：`ticks=480`、**1 原子(1/4 拍)=120 ticks** ⇒ `bpm=60/part`，四分音符恰好 = `part` 秒，全是整数 tick，零误差。

### (b) `.mid` → `type:"midi"` JSON（并修掉丢音）
1. **自带 SMF 解析**：MThd/MTrk、running status、tempo map；`note on vel=0` 视为 off。
2. 取 **`ticks=1000` & `bpm=60` ⇒ 1 tick = 1 ms**；时刻 = 毫秒四舍五入。比 480 好，不用再跟源 BPM 较劲。
3. **映射**：先八度折叠进 48–83，再把半音吸附到相邻音阶音（方向用上下文，平票向上）。
3.5 **⭐⭐ 短半音倚音簇：整簇删除（四种做法试遍后用户定的）**
   源里的**半音接近音**是「长音 → 短音 → 黑键短音 → 长音(目标)」的固定句式：
   案例《月亮代表我的心》源 AltoSax `G4(385ms) → G#4(96) → A4(96) → A#4(955)`，-3 移调后 `E4 → F4 → F#4 → G4`。
   四种做法用户逐版听过（**别自己拍，听感只能用户验收**）：
   | 做法 | 结果 | 用户反馈 |
   |---|---|---|
   | ① `snap` 吸附 | `F4@20.013 → G4@20.109`（只隔 **96ms**）| ✗ 假连音 |
   | ② 只丢黑键、保留原间距 | `F4 → G4` 隔 199ms | ✗「还是怪，拉长间距并不合适」|
   | ③ 折成同刻和弦 | `(F4+G4)@20.212` | ✗「还是怪，这个滑音好怪」|
   | ④ **整簇删除（含簇内的调内短音）只留目标音** | `mi → so` | ✅ 采用 |
   ✅ **最终取法（两步）**：
   a. 短音簇（≦250ms、相邻间隙<150ms）**整簇丢**，**不只是丢黑键那个**；
   b. **把装饰音占的时间还给目标音** —— 目标音起点提前到簇首那个音的时刻。
      不还时间的话，删完会露出空档：实测 `E4@19.615` 直接到 `G4@20.212` = **597ms**，
      用户一句「E4→G4 是不是稍微有点长」——因为被删的两个滑音音本来就占了那 200ms。
      提前后 5 处全部变成 **385–397ms（正好一个八分音符）**，与其它乐句脉动一致。
   只在簇内**含黑键**（移调后不在调内）时触发 —— 全白键的短簇（如 `6̣7̣1` 拔句）是源谱本来的跑动，**原样保留**。
   不属于任何簇的孤立短黑键：丢弃。实测该曲 5 处簇（删 10 音）、1 个孤立音，校验 0ms。
   自查命令：把成品的按下事件按时间列出，比「主旋律相邻两音的间隔」是否回到一个八分音符。
7. **⭐ 自己加的伴奏/低音线，不能与旋律「同键重叠」** —— `convert` 会把同键重叠区间合并，
   合并后按下时刻取两者的**最早** → 旋律的击弦被吞掉、起点被提前（实测《月亮代表我的心》342 个低音里有 **77 个**
   与旋律同键，旋律起点最多被拉早 385ms）。**规则：低音让路** —— 低音若与某条旋律音同音高且时间重叠，就删掉这个低音。
   对称地：任何「伴奏声部 + 旋律」的双层输出都要跑一遍这个检查，合并数不为 0 就排查。
4. **同键重叠区间合并** —— 只在**真重叠**时合并（`s < end`）；**相邻不重叠 = 重新击键，绝不能合并**，
   否则一串重复音会变成一个大长音，节奏全丢。
5. 同键重击由**数据自己**保证 ≥30ms 间隔（见 §4c）。
6. **⭐ 裁掉开头的空拍** —— 源 MIDI 常把曲子放在第 3 小节开始（1–2 小节前导静音）。
   实测《月亮代表我的心》：**全部 17 轨的第一个 note-on 都在 tick 960**（div=120 ⇒ 2 小节 = 6.154s），
   不裁的话 BetterGI 一按播放就是 **6 秒干等**，用户会问「为什么开头一大段空白」。
   做法：**只在第一个事件的 delta 上做整毫秒平移**（`delta0 -= 首音ms - 300`），其余事件一个字节都不动 ——
   重新对所有时间做加减会因毫秒取整变化打乱「同刻事件」的巧合，破坏 `U@0` 占位的插入条件，
   进而触发解析器的 30ms 游标分支（实测：浮点平移 5854.0000001ms 就会踩）。留 ~300ms 起手，别让首音正好压在 0。

### (b2) ⭐ 外部钢琴 MIDI（midishow/虫虫 下载的双手谱）→ 曲库
这类谱常是**两手两轨 + 带升降号的调**（实测《香水有毒》= F 小调，61% 音是黑键）。**别直接 snap**（会改音高）。
正确做法是**整首移调到白键调** —— 移调保音程，snap 不保：
1. **判调性**：统计全部音的 pitch class，看落在哪个调的 7 个音上（如 {0,1,3,5,7,8,10} = Ab 大调/F 小调，同套音）。
2. **选移调量** = `(0 − 主音) mod 12` 的同余类（F 小调 −8 ≡ +4 → A 小调），
   再在同余类里**选折八度最少那个八度**（实测 −8 只折 1/535，+4 要折 175/535）。
3. **选主旋律轨**：看每轨「每 onset 的单音比例 + 音域」——旋律轨单音多、音域靠上而窄
   （实测轨1 72% 单音、G#3–C7 = 主旋律；轨2 琶音 = 左手）。要更丰满可整轨（旋律+和声，同按 ≤3 可用）。
4. `m2.convert(notes, "snap", transpose=移调量)` + `verify_intervals` 强校验（偏差应 0ms、折叠 ≤ 个位数）。
   **两手一起转时：左手（伴奏轨）整体升/降一个八度再并入** —— 钢琴双手谱跨 4–5 个八度，
   直接并（《香水有毒》t1+t2）要折 387/1524（25%）；左手 +12 后再并只折 **55/1524（3.6%）**。
   两手各占琴的一个八度，相对八度关系变了但琴本来就装不下，听感反而干净。
4.5 ⭐ **三层缩编定式（双手钢琴谱最常用，实测一次过）**：右手每个音头取**最高的 2 个声部**
   （第 1 个 = 旋律；第 2 个 = 内声部，且**必须低于此刻正在响的旋律音** —— §8.4-7a 的天花板规则，
   否则旋律拖长音时伴奏会被顶成新旋律），左手只取**每个音头的最低音**并折进 **C3–B3**（低音区）。
   实测《天路》（192s 双手谱、Eb 大调、−3 半音 → C 大调）：978 按键 / 密度 5.10 音/秒 / 最大同按 4 键 /
   低音键占 54% / 音域 **C3–B5 用满琴** / **0 折叠 0 吸附 0 滑音**（源谱调内音 99.2% 时，整首移调就是零处理）。
   ⚠⚠ 左手若是**琶音织体**（每音头都在响，实测 2.8 音/秒），**别原样搬**：源谱左手常跨 2–3 个八度
   （实测 C2–C5），而琴的低音带只有 **C3–B3 一个八度** → 同音级的高低音（C3 与 C4）**塌到同一个键上**，
   那个键被每 0.5 秒敲一次，用户听成「莫名的重复音」（他会直接来问）。
   **做法（两条，别自己选）**：① 手术式：只改他点名的地方（`references/surgical-edit-on-landed-json.md`），
   **保琶音织体**；② 全局面：左手按 **0.5 秒分箱、每箱只留最低音**，**且与上一个低音同键就不再按**
   （同键不重复按 = 让它当长音挂着，由和弦重拨维持）。实测全局面：低音 529 → 253、
   全曲「1.6 秒内同音连按」530 → 251、按键 978 → 647、密度 5.10 → 3.39、最大同按 4 → 3。
   ⚠⚠ **② 会把低音从琶音织体变成低音线（“没那么厚”），用户实测会退单并要求换回琶音版** ——
   所以默认只做①；要做②先报代价让他点头。判据、验证指标与“为什么不是密度问题”见 §8.4-11。
   变体版都渲 mp3 发进聊天、选中的落库，其余留在 `scores/<曲名>/`（用户会明确说「换回上一版」）。
5. **A/B 试听再定**：主旋律 vs 旋律+和声 vs 双手完整，渲成 mp3 让用户耳朵选（听感只能用户验收）。

**坑**：`m2.convert` 的 notes 元素顺序是 `(start, end, pitch, track, ch)` —— 写反会喂进垃圾音高，
`fold` 的 while 循环几乎不收敛 → **直接卡死**（实测连续两次 300s 超时）。

### (b3) ⭐ 多轨 GM 编曲 MIDI（十几轨 + 鼓轨 + 旋律在多件乐器间轮换）→ 曲库
判据：`--list-tracks` 打出十几行、每轨一个独立通道、音域从 33 铺到 96、
**有一条音符很多的轨没有 Program Change**（= 通道 9 鼓轨，必须排除）。
**别整轨转**（实测钢琴轨 5.5 音/秒、八度折叠 27%、最大同按 9 键 → 糊）。做法：
1. `python <skill>/scripts/list_midi_gm_tracks.py 歌.mid` 一次打出「通道 / GM 音色 / 音符数 / 音域 /
   单音比例 / 活跃区段」→ 认出旋律乐器、钢琴、贝斯、鼓、琶音伴奏。**看输出，别猜**。
1.5 ⭐ **同音色的第二条轨先当「延迟回声」查，别当二重奏**：老 GM 编曲（PsmPlayer 时代那批）常整条复制主旋律、
   往后挪约一个八分音符当回声轨。判据：拿 B 轨每个音的 `(时刻, 音高)` 去 A 轨里找 `t − Δ`（Δ≈0.25s）处
   是否有同一个音，命中率高 → **整轨丢掉**（保留 = 旋律每句都拖一个影子）。
   ⚠ 别用「同刻同音高」的比例判独立性：实测只有 15% 同刻，看着像两条独立声部，其实全是回声。
2. 主旋律 = 各旋律乐器轨的并集，按 `(onset, 音高)` 去重：**同音高、起始差 <100ms 的只留一个**
   （多件乐器叠同一旋律常错开 30–50ms；该速度下真实重复音至少隔一拍，不会被吃掉）。
3. 自检：全曲无 >1.5s 空档；**同一乐句必须在不同段落逐音复现 3–4 次**（不复现 = 抽错轨）。
4. 调性用**时长加权**的 pitch-class 直方图判（大调/小调一起看），并**跑 §1.4 的移调扫描表定移调量** ——
   落点选「黑键 0%」那一行（否则只能 snap 改音高），再在 ±12 里挑音区；只能整八度叠加。
5. 音区**别自己拍**：各乐器各用自己的八度，抽出来会逐句跳八度 →「逐乐句 ±12 对齐」是一版，
   另交一版「忠实原八度」，**渲 mp3 让用户选**（听感只能用户验收）。
6. 交付前**跟公开 C 调简谱逐音核对** —— 一次同时验证「抽对了轨」和「移调量对」。
   快路：用**歌词锚点**搜 `"<曲名> 简谱 <歌词片段>"`（搜索摘要里常直接带出歌词逐字对齐的级数），
   别一上来就下谱图读图（详见 reference）。
   ⭐ **结构性指纹比逐音对谱更快**：找副歌里「**同一音级连按 N 次**」的 hook（实测《江南》
   「圈圈圆圆圈圈 / 天天年年天天」＝同一音级连按 12 次），两版之间 / 与简谱里这个**连按次数 + 音级**必须一致 ——
   一次同时验明正身、验移调量，还能当两版之间的**对齐锚点**（§7.3）。
7. **交付 = 先入库一版 + 再挂 mp3 待换**：把**层数最少、密度落在 3–5 音/秒**的那一版直接写进
   `完整曲库/05_我的新增/`（用户手里先有一份能弹的），其余变体只渲 mp3 发进聊天。
   只丢一堆 mp3 不给成品，用户会问「所以到底哪版入库了」。
全文（GM 音色角色表、逐乐句移八度的三个反例、权威谱核对与防盗链绕过、贝斯为什么装不进低音八度）
→ `references/multitrack-gm-midi-melody-extraction.md`。

### (b4) ⭐⭐ 单轨密集编曲 MIDI（「素材库」导出、一轨塞满所有声部）→ 曲库
判据：`scripts/list_midi_gm_tracks.py` 只打出**一行**（或一条轨 n=几千）、**音域跨 5–6 个八度**、
密度 **15–20 音/秒**、每音头 3–5 个音。**没有旋律轨可读，旋律只能自己抽** —— 这是本类活儿最大的风险点。
先跑 `scripts/scan_midi_structure.py 歌.mid`（结构 / 调性 / 顶声部音区带 / 重复扫描一次出全），然后：
0. ⭐⭐ **抽旋律是最后手段 —— 先主动问用户有没有「轨分得清」的版本**。抽旋律是唯一的关键假设，猜错全盘白做；
   而同一首歌的**双手钢琴谱 / 多轨全曲版**往往是现成的。实测同一天拿到的两份《天路》：单轨密集版
   （7427 音、6 个八度、整首弹两遍、调内音覆盖率仅 89%）→ 换成随后用户给的**双手钢琴谱**（轨1 右手 = 旋律+和声、
   轨2 左手 = 伴奏、192s 与歌曲等长、Eb 大调覆盖 99.2%）后：**0 黑键音 / 0 折叠 / 0 吸附**，一次过、
   连滑音都没用上。**做法**：报「这份要我先猜旋律在哪」时**同时报出四项量**（轨结构 / 时长是否=歌曲真实长度 /
   音域跨度 / 调内音覆盖率），再问一句「有没有轨分得清的版本（双手钢琴谱、全曲版）？」——
   用户手里常常有，换过去能省一整天。别把「难啃的文件」当默认前提硬做。
1. ⭐ **先测「整首是不是弹了两遍」** —— 素材库文件常把整首歌复制一份接在后面（实测 3:08 的歌做成 6:55）。
   做法：拿**顶声部**（每音头最高音）在 +dt 处找 ±0.2s 内是否有同音高，对 dt 扫描；
   真偏移处命中率会**从 5–16% 跳到 80%**（实测 +188.0s = 600/750，其余 dt 全 ≤16%）。
   判到 ≥60% 的 dt → **只保留第一份**（不砍的话游戏里会老老实实弹两遍），并在 `description` 里写明「源文件含重复的一半，已裁」。
   ⚠ 别用「逐秒平均音高」这类粗指标判重复：实测最大偏移处也只有 19%，会把重复漏掉。
2. **抽旋律 = 每音头最高音 + 音区带过滤**：先看顶声部的音高分布，找到主带的中位音，
   只保留 `[中位−9, 中位+12]` 半音内的音当旋律（带外的音头视为「此处旋律没在响」）。
   实测：顶声部在「只有伴奏低音在响」的音头上会掉到 F#2（钢琴左手），**必须过滤**，不能直接当年旋律。
3. ⭐⭐ **抽完立刻让用户确认，再做后面的（对谱/调性/滑音/缩编）** —— 单轨抽取是唯一的关键假设，错了全白做。
   交付方式：只渲 30–40 秒两版 mp3（**旋律单独** / **源谱原样**）发进聊天，问一句「旋律抽得对吗」。
   别指望 §5 的强校验能兜底 —— 它只证明「忠实于源 MIDI」，证明不了「这是这首歌的旋律」。
4. **量化「全谱原样搬」的后果再谈缩编**：实测该文件全谱原样 = **最大同按 13 键**（根本没手指弹得出来）→
   缩编不是可选项。可用 §6 的「每刻留最高音 + 相隔 ≥14 半音的低音」起手。
5. 调性用**全谱** pitch class 覆盖率判（实测 Eb 大调 89% → 搬进白键只要 −3），再跑 §1.4 的移调扫描表定移调量；
   之后接 §4(b3) 的缩编 + §8.4 的按段/滑音流程。

### (b5) ⭐ FF14 诗人谱 MIDI（文件名常带 `【ff14】`）→ 曲库
判据：`scripts/list_midi_gm_tracks.py` 只打一行 / 一条轨；**每个音头只有 1 个音**（单音线，最大同按 ≤2）；
音域大致 C3–G5；密度 3–4 音/秒；**所有音符时值都 ≈70ms**（统一短音 + 极细时间网格 = 机器痕迹）。
做法（实测《传奇》949 音 / 252s / E 大调）：
1. **移调量照 §1.4 跑扫描表**，别拿直方图肉眼判 —— E 大调 → `−4` 与 `+8` **同余类、音高内容完全相同**：
   实测 `−4` 落到 C3–D5（低音区用满、最低 82 个音要折上一个八度）、`+8` 落到 G#3–D#5（只折 4 个高音、低音区空着）
   → **两版都渲 mp3 让用户挑**，别自己拍。
2. ⚠ **如实报「残余变化音」**：这类谱常有借用和弦的调外音（实测 5.4% = 51 个），移调**去不掉**、只能就近 `snap`。
   汇报写「整首 −4 移到 C 大调（音程保真）+ 5.4% 变化音被吸附」，**别写成「无损」**。
3. **源谱的 70ms 短音别自作主张拉长** —— 游戏里按下即出声、靠余韵，拉长反而糊。
   （与 §8.2b 给「补出来的低音」补时值不矛盾：那是新造的声部，这不是。）
4. 首音在 0.000s → 平移到 0.3s（§4b6），其余字节不动。
5. 交付时**先说织体**：单音线里旋律与伴奏是**交替**弹的（竖琴独奏织体）→ 提前说明「听起来像竖琴独奏、不是纯人声旋律」，
   不说清用户会以为抽错了声部。

### (c) ⭐⭐ D/U 语义与 30ms 陷阱（不看这段就会交一批全坏的谱）
- **`D` = 按下(KeyDown)，`U` = 抬起(KeyUp)**（源码 `AddExplicitEvents(..., bool isDown)` 配 `status == "D"`）。
  每个音符是「**起点发 D、终点发 U**」。写反了谱子照样能被解析、列表也显示正常，但每个键都在音符**结束**时才按下 —— 音符整体平移、糊成一团。
- midi-JSON 路径（`ParseMidiJsonTimeline`）**不做** `Normalize`/`ApplyRepeatedKeyGap`，只有解析时的两个 30ms 分支：
  - 分支A `D` 紧跟 `U` 且同键、延迟 <30ms → `cursor += 30ms`
  - 分支B `U` 后紧跟同键 `D` 且自身延迟 ≥30ms → `cursor -= 30ms`
  两者**只在同刻 U→D 时互相抵消**；其它情况都会**永久移位全局游标**，长曲可累积到上百秒（「越弹越快」）。
- 对策（两条一起做）：① **自己在数据里保证同键重击 ≥30ms 间隔**（把前一个音的抬起提前）；
  ② 在任何「`U` 后紧跟同键 `D`」之间插一个零时长、不产生事件的占位事件 **`U@0`**
  （parser 里 `keys == "@"` 时 `AddExplicitEvents` 不执行，也不污染 `previousKeys` 同键比对）→ 两个分支都不触发。
- **30ms 时长下限要在「区间阶段」就钳**，不能在发射阶段钳：源 MIDI 里真有 1ms 的音符，发射阶段钳会让它的「抬起」
  跑到下一个同键音「按下」之后 → 同键连续两次按下 + 孤立抬起。钳完若与下一音重叠，交给合并逻辑处理。
- 同刻事件一律 **先 `U` 后 `D`**。

### (d) 模式取舍
`snap`（默认可演奏率 100%，但半音被改，**音高会变**）/ `drop`（复刻原行为，对照用）/ `raw`（只折叠不吸附，保真但仍丢音）。
**必须如实说明：snap 是「能演奏」而非「原汁原味」。**
> 例外：如果整首歌只差一个**非八度的调性**（见 §4b2），**整首移调**才是无损解，别用 snap。

### (e) ⭐ 用户说「节奏稍快 / 稍慢」→ 校速**只改 `ticks`/`bpm`，音符数据一个字节都不动**
先量再答，别凭印象：
1. **量成品的「基本音符时值」**：按下事件按时刻排序，取**相邻时刻差的众数**（它是个阶梯——
   实测光遇版 221 / 442 / 884ms ⇒ 基本单位 **221ms**）。这个数就是成品的一个基准音符值。
2. **原曲 BPM 要双源核对**：① BPM 数据库（搜「<曲名> BPM key」，`tunebat` / `songbpm`）；
   ② **用户本地那份全曲版 MIDI 的 tempo meta**（`parse_smf(...)["tempos"]`，500000µs = ♩120）。
   两个都指向同一个 BPM 才算数。原曲的八分音符 = `60000/BPM/2` ms（♩120 ⇒ **250ms**）。
3. 比值 `f = 原曲八分 ÷ 成品基本单位`（实测 250/221 = 1.13，与用户「有点稍快」的听感对上）。

校准手法：**只改 JSON 顶层的 `ticks` / `bpm`** —— `1 tick = 60000/(bpm×ticks)` ms。
想放慢 f 倍就令 `bpm × ticks = 60000/f`，用整数凑：f=1.136 → `bpm="55", ticks="960"`（60000/52800）。
- **别去改音符数据**（把所有 Δ 乘 f 再取整）：毫秒取整会在长曲累积偏移；改 `ticks` 是零误差的等价手法，
  `Δ=0` 的同刻事件**一个都不动**（`U@0` 占位条件、30ms 游标分支全不受影响）。
- 同一首歌的两个版本可以各设各的：实测 221ms 网格那版用 `55/960`、240ms 网格那版用 `60/960`。
- 收尾：`description` 写明「速度校准：按原曲 ♩=120（bpm=55, ticks=960，放慢 13.6%，数据未改）」；
  清单 CSV 备注加同一句，且**写成幂等**（先判重再追加 + 先判重再拼接，否则重跑一次就多一句）。
- ⚠ **试听必须跟着校速走**：`render_preview.py` 只按 Δ 解码、**不读 `bpm`/`ticks`** →
  校速后的谱要**先把绝对时刻乘 f 另存一份**（由 `press_intervals` 取 `(d, u, key)` → `(d*f, u*f, key)` 重建 notes）再渲，
  否则发出去的 mp3 还是老速度，用户会说你根本没改。
- ⚠ 校速会改变**总时长**（实测 3:24 → 3:53）：要主动说明「是速度，不是截短/加长」。
- ⚠ 校速 ≠ 结构对齐：若两版段落长度本来就不同（§7.3），放慢只会让基准音符对上，**别顺便吹「和原曲一模一样长」**。

## 5. 校验方法（没有 C# 环境时怎么验）⭐
**「按键合法 + 时间单调」是假通过** —— 它对 D/U 写反完全免疫。必须做：
1. **位级复刻 `ParseMidiJsonTimeline`**（含上面两个 30ms 分支）重放生成的 JSON；
2. 从重放事件重建**每键按下区间** `[(down_ms, up_ms)]`（按 `D`=按下配对），与源谱**逐键逐条比对**，
   偏差 ≤2ms；D/U 写反会在这里暴露成「整首错位」；
3. **时间轴零漂移不变量**：比较「含 30ms 分支的复刻重放」与「纯 delta 解码」的时刻，每个按下事件处都不得有偏差；
4. 按键 ⊆ 21 键、事件时间单调；`.mid` 用文件头 `MThd` 校验。
5. ⭐ **跟权威谱交叉核对** —— 上面 1–4 只能证明「忠实于源 MIDI」，证明不了「这是这首歌的旋律」。
   把旋律转成首调级数，与公开 C 调简谱逐音对；**§4(b3) 的多轨抽取必须走这一步**
   （做法 + 谱图防盗链绕过 → `references/multitrack-gm-midi-melody-extraction.md`）。
坑：别拿「含 30ms 分支的重放」去和源谱比**绝对时刻** —— 那个分支会全局累积，会误报成几十秒偏差。
坑：`convert` / `to_midijson` / `verify_intervals` / `press_intervals` **全部吃「秒」**。自己拼中间产物时
把毫秒当秒喂进去，会得到一份**自洽但整体放大 1000 倍**的文件，而 `verify_intervals` 照样打印「OK 偏差 0ms」
（两边错得一样，比值自然一致）→ **校验通过 ≠ 单位对**。自查：成品的末事件时刻应与源时长同量级，差 1000 倍就是这个坑。

## 5.5 ⭐ 用户抱怨 → 90 秒定位（**先查谱面数据，别先钻 BetterGI 源码**）

⭐ **「重复」类抱怨：先证再改，别默认砍结构**。流行歌的常见写法就是复用：实测《江南》主歌 8 句只用了 4 条旋律
（第 1 句的公式在**第 1/5/7 句**原样复用）、前奏那句乐句原曲**走两遍**（约 16 秒，人声 18.5s 才进）——
纯器乐版会听得很明显，靠歌词盖住才不觉得。**证明路径**：文本简谱抽级数串 → 子序列定位各句公式；
全曲版 MIDI 量前奏长度。确证是原曲的 → **先说清「这是原曲的写法」并给证据**，再另交一版
「前奏只走一遍」的候选让用户挑，**不要悄悄删他的结构**。

**顺序很重要**：本 skill 第 5 节那几条（纯 delta 解码 + 相邻按下间隔分布）几秒钟就能证明「谱面数据干净不干净」；
**先证谱面，再怀疑播放端**。教训：为了「和弦听着有先后」去通读 BetterGI 的 `MusicPlaybackService` /
`PostMessageChannel` / `MusicConfig` 整套源码，结论却是**谱面本来就干净**（同一刻的按键 delta=0、解析器保序），
白花一小时 —— 而真正的两个原因都在谱面数据里（§4b3.5 假连音、§4b6 前导空拍）。
另：`MusicConfig.InputMode` 默认 `BackgroundPostMessage`（后台投递窗口消息），前台 SendInput 是另一个模式，
但它**不是**这两个症状的原因，别拿它当万能解释。

### 5.6 ⭐⭐⭐ 「基准音 + 弯音」写法的旋律：必须读 pitch bend（2026-10-17 稻香事故，用户提示后才发现）

**症状**：用户说「**这个 MIDI 我听了没问题**，但你抽出来的旋律音不对（少了个高音）」。你抽出的旋律看起来是
**同一个音反复**（如 `A3 B3 B3 B3 B3 B3 A3`），而且怎么调都对不上原曲。

**根因**：编曲者把旋律写成「**一个基准音 + 弯音自动化（pitch bend）**」——音符事件只记基准音，
真实音高变化全在 `0xE0` 事件里（DAW 钢琴卷帘上就是那条上下起伏的蓝线）。
更隐蔽的是**弯音范围往往不是 GM 默认的 ±2 半音**，而是用 RPN 设成了 **±12 半音**：

```
稻香.mid 实测：轨2（人声）弯音事件 200 个，值域 -2048 ~ +1408
              RPN 弯音范围 = ±12 半音（通道 2/3）
              ⇒ 实际音高变化 -3.0 ~ +2.06 半音
              基准 B3 + 2 半音 = C#4  ← 就是用户听出来的那个高音
```

**⚠️ 本 skill 的 `tools/midi_to_midijson.py:parse_smf` 不处理弯音**（遇到 `0xA/0xB/0xE` 只跳长度就丢），
所以**所有依赖它的构建脚本都会漏掉这类旋律**。可用实现见 `scores/稻香/bendlib.py` 的 `corrected_notes(path)`。

**90 秒识别（动手前先跑）**：
1. 统计候选旋律轨的**相邻同音率**：>30% 就要怀疑（正常旋律重复音有，但不会整段同音反复）。
2. 直接数 `0xE0` 事件：`grep` 不行，用 `bendlib.parse_track()` 或现成的
   `scores/稻香/check_rpn.py <midi>`，打印每轨「弯音事件数 / 值域 / RPN 范围」。

**正确读取（三件事缺一不可）**：
1. **弯音值**：`value = (msb<<7)|lsb`，半音数 = `(value-8192)/8192 × range`；
2. **range**：跟踪 RPN —— `CC101=0, CC100=0, CC6=v` → 该通道 range = v 半音（未设则 ±2）；
3. **note-on/off 配对**：`0x8` 是 off，`0x9` 且 **velocity=0 也是 off**。
   ⚠️ 我只用 note-on 列表配对（on-on）时，时值全是垃圾（有 0、有几千 ms），
   再经过 35ms 规则就变成**全谱 30ms 点击音**（跟 §0.5⑤ 的 bug 表现一模一样，但根因不同）。
4. 取**音符时值内弯音的中位数**（不要取起音瞬间：滑音写法下起音常常还是基准音），再 `round()` 到半音。

**验证判据（用用户报的那句核对）**：`D5 D5 D5 E5 C5` → 修正后应能在对应位置打出 `E5`。
稻香修好后：25.91s 出现 `E5(366ms)`，1440 个音里有 61 个音高被弯音改变（4%）。

**教训**：用户说「源没问题、是你的问题」时，先信他 —— 去查**元数据通道**（pitch bend / RPN / CC / 移调 meta），
而不是继续在音符事件上调对齐算法（我在 DTW 和锚点内插上白花了两轮）。

## 6. 转换前先量「密度 + 音域」—— 否则交出去会「糊」
- **密度（音符/秒）**：官方谱/键谱一般 **3.7–5.1**（实测官方 lemon 3.66、春日影 3.72、卡农 5.06）。
  完整钢琴改编常见 **10–12**（WindSong Lemon 源 MIDI 11.88）→ 直接转就是「音太多、很乱」。
- **音域**：琴只有 **C3–B5（3 个八度）**，源 MIDI 常见 C3–G7（4.5 个八度）→ 超出的音被折叠，
  **旋律被打散到不同八度**（实测 215/2088 个音需折叠）→ 也是「乱」的来源。
- 另查：超短音（<50ms 装饰音）数量、因半音被吸附的音数（每吸附一个 = 一个错音）。
- 源 MIDI 常常**所有音都在一条轨上**（另几条轨只有 meta）→ **无法按轨拆旋律/伴奏**，别指望 `--tracks`。
  单轨密集编曲（素材库导出那种）的抽旋律流程、以及「整首是否弹了两遍」的检测 → §4(b4)。

精简选项（改前先问用户，别自作主张换掉他手里的版本）：
- **每刻留最高音 + 相隔 ≥14 半音的低音**：密度降到 ~7，**不依赖旋律假设**，最安全。
- **每刻只留最高音**：降到 ~3、最干净 —— 但 ⚠️ **「每刻最高音 = 主旋律」不总成立**。
  用**时长中位数**验证（主旋律通常最长）。反例：WindSong Lemon 最高层中位 352ms、其它 427ms → 最高层反而是伴奏织体。
  没把握时**把候选版本交给用户耳朵定**。

## 7. 去重与选版

### 7.1 跨来源去重
- 规范化曲名：NFKC → 去括号内容 → 去版本词（修改版/缩编版/和弦版/C调/单音…）→ 去随机码 → 去标点空格。
- **随机码识别**：官方文件名为「曲名 - LZ5hp0vW」。判据要「含数字 **或** ≥2 个大写字母」，
  否则 `magnet`/`Summer`/`Air` 这类真曲名会被误删（实测踩过 `泽野弘之 - aLIEZ` 被删成 `泽野弘之`）。
- 保留优先级：官方 JSON > 转换产物 > MIDI > 其它；只**复制**保留份，**不动原文件**。
- 再跑一轮模糊匹配（包含关系 / 编辑距离≤2）作为「疑似同一首」清单给用户定夺，**不要自动合并**
  （卡农 vs 圆号卡农、小星星 vs 小星星变奏曲都是不同曲）。
- **官方源优先 ≠ 一定更好**：曾按「官方优先」把官方那份坏 lemon 留下、把调性正确的 WindSong 版丢掉。
  → 重复项筛选要加一步「**调性中心是否合理**」的检查（见 §8.3）。
- 非目标格式（Sky/覆盖层 `.txt`/`.json`）单独归档，别混进曲库。

### 7.2 大合集必然重复：选版评分
光遇类合集重复率极高：15,116 份归一化后 **1,867 组重复、涉及 5,918 首（41%）**，《大鱼》16 版。
直接挂给用户 = 「同一首好多版本，哪个好？」→ 必须预先去重并给出**可解释**的选版依据。
- **评分写进 CSV 的「评分依据」列**（用户能逐条查）：档位 A/B/C = +35/+28/+10（**档位差刻意只给 7 分**，
  不能压倒完整度）；时长 +时长/10（封顶 30）、音符数 +音符/80（封顶 12）；八度折叠比 −比×1.2；
  密度偏离 4.5 −偏离×4（<2 再 −15）；最大同按 >2 −(同按−2)×4；标题干净 +3 / 版本词 −3 / 有署名 +3。
- **坑 1**：**空谱靠「时长」拿高分**（实测《麻醉师》15 音/391s 排第一）→ 在**分档阶段**就拦掉（音符 <30 或密度 <1）。
- **坑 2**：**「精选」目录要拷转换后的 MidiJson，不是原始 Sky 谱** —— 原始谱带 `columns`/`songNotes`，
  拷错体积胀 10 倍（实测 690MB vs 63MB）。→ 迁移报告里**记一列输出文件名**。

### 7.3 ⭐ 同一首歌拿到两个来源，用户问「能拼起来吗」—— 先判再答
「光遇那版完整但没低音，我找的这版有低音但短，能结合吗？」→ **默认答案是「mosaic 拼不了，但能给长的那版补声部」**。先跑两条判据：
1. **短的那份是不是「本身就是完整的短编曲」**：看结尾有没有**终止式**（收在主音上 + 长时值）。
   有 → 它已经把整首歌讲完了，接不到长版后面。**别把「短」默认当成「被截断」**。
2. **两版段落长度是否一致**：找同一个 landmark（最稳的是 §4b3-6 那个「同一音级连按 N 次」的副歌 hook，两版都数得出来），
   再比**两个 landmark 之间的时长**。实测《江南》：副歌 43.0s / 102.2s（光遇版）vs 42.9s / 86.4s（MIDI 版）——
   第一个点几乎重合，**但两副歌之间 59 秒 vs 43.5 秒** → 不是统一快慢，是段落长度不同。
   比值不恒定 ⇒ 时间轴对不上 ⇒ **贝斯/伴奏一个音都不能按同一时间轴搬过去**（搬了就配错和声）。
   ⚠ 别拿「开头对得上」外推：两版都从曲子开头写起，首句时间差 ≈0 很正常。
- **用户要的是效果（全曲长度 + 低音），不是字面拼接** → 直接给长的那版补它缺的声部（§8.2b），
  同时**用上面两条判据的实测数字说清为什么拼不了**。用户认的是证据，不是结论。
- 用户仍坚持要用短版那条真·贝斯线时：可以做，但必须提前声明**段落映射里有推断成分**、要他听两遍验收；
  别悄悄按「比例缩放」铺上去 —— 段落长度不同时那是错的和声。
- ⭐ **判「两版是不是同一首歌 / 同一段落 / 差多少速度」用 DTW，别靠听**：两版各抽**顶声部级数串**
  （音高折成 1–7 级数、忽略八度；非 C 调按它自己的调读级数），跑一遍 DTW，看
  **代价 ÷ 长度 = 失配率** 与 **对齐路径的时间映射**。判读：
  - 时间映射**平滑单调** + 失配率 ≲0.5 → **同一首歌**（残余失配基本是顶声部抽取噪声，不是歌不对）；
  - 代价高 **且** 映射乱跳 / 大量一对多 → 不是同一段，或结构根本不同。
  实测：光遇版《江南》顶声部 ↔ 用户那份 4:02 全曲版 = 272/722、映射线性（1.19 倍速）；
  光遇版《传奇》↔ FF14 版 = 平滑 1.08 倍速 ⇒ 两两确认同源。
  **斜率稳定 = 纯速度差**（→ 走 §4e 校速）；**斜率在分段处跳变 = 段落长度不同**（→ 回到本文第 2 条，别搬声部）。

## 8. 整库级操作

### 8.1 光遇 15 键 → 原神 21 键（整库迁移）
工具 `tools/sky_batch_migrate.py`。实测 15,116 份：**可弹 96.3%、零改动 26.1%**。
**为什么几乎无损**：两边都是纯 C 大调；唯一差异是光遇最高音 **C6(84) 超出上限 B5(83)** → 折下八度即可。
全库实测**半音吸附 0 处、原映射率 100%**。

**分档规则**（脚本自动分流，不让用户手挑）：
| 档 | 条件 | 处置 |
|---|---|---|
| A 丝滑完美 | 零折叠零吸附 + 时长≥25s | 写盘（建议先只挂这档） |
| B 仅折叠最高音 | 零吸附、有八度折叠 | 写盘（3,862 首折叠≤5 个音） |
| C 短曲 | <25s | 写盘 |
| D 不适合 | 密度 >10 音/秒、含变化音、解析失败、多乐器谱 | **不写盘**，只进报告 |

**坑**：
1. **文件名去重必须大小写不敏感**（Windows）：按 `(子目录, 文件名.lower())` + `os.path.exists` 兜底。
   否则 `Song`/`song` 互相覆盖 —— 实测「报告 14,555 但只落盘 13,911」。**落盘数必须与报告数逐档对账**。
2. **路径分隔符**：报告里的相对路径是 `\`，按 `"Chinese/"` 匹配会全失败 → 先 `.replace("\\","/")`。
3. **只迁 `Songs/`**：`Multi-Sheet Songs/`（多乐器，需两人合奏）与 `VSRG/`（节奏游戏谱）单人弹不了 → 排除并告知，别静默丢。
4. **产物单独放**（`试验_Sky/`），**绝不直接倒进用户的维护曲库**。上万首一起挂给 BetterGI 会明显变慢，建议先挂 A 档。
5. 写盘前每首跑 §5 强校验；跑完再抽 250 首**从源谱重转、逐字符比对**。
6. 光遇谱 `pitch` 字段（"C"/"Ab"）是光遇乐器自己的调音，**转换时忽略**（游戏里按键位发声）。
   四种格式都要支持：顶层 JSON 数组 / `{"songs":[…]}` / v3 composed `songNotes=[{"key":"1Key4","time":100}]` /
   v2 recorded `notes=[[keyIdx,timeMs,"1"]]`；**文件后缀是 `.txt` 但内容是 JSON → 按内容嗅探**。
   ⚠ 有的文件 `notes` 与 `songNotes` 同时存在且重复 → 只取 `songNotes` 并 `sorted(set(ev))`，否则音符**翻倍**。
   光遇 15 键音高表：`[60,62,64,65,67,69,71,72,74,76,77,79,81,83,84]`（C4–C6）。
7. **同刻和弦里除最高音外，时长全是 30ms** —— 这是**机器痕迹**，不是原谱意图：Sky 谱只给按下时刻，
   转换用「按住到下一个事件」推导时长，而同刻和弦成员之间 gap=0 → 被钳到 `MIN_NOTE_MS`（实测《答案》占 219/724 音，
   恰好等于「和弦内非最高音数」）。**原样播放不影响**（拨弦音自带余韵、游戏里按下即出声），
   别把它当「原谱就是断奏」去解释。
   ⚠⚠ **但只要你把这些音拿去做声部（典型：下移八度补低音），就必须先给足时值** ——
   30ms 的音在整体电平里几乎不存在：实测《江南》光遇版 376 个和弦声部直接下移八度后，
   「低音覆盖时长」只有 **3%**（用户听下来依旧是「还是没低音」）。改法见 §8.2b 第 3.5 条。

### 8.2 ⭐「迁移后一个低音键都没有」——先量再答
**光遇 15 键的最低音就是 C4(60)**，而原神低音区是 **C3–B3(48–59)**，两者**零重叠** →
实测 10,195 首**全部**不含低音键（Z X C V B N M）。用户听感是「你转的曲子都没有低音」（会直接来问）。
- **先量再答，别猜**：按目录统计「含低音键的文件数」——官方/MIDI/键谱来源通常 96–100% 有低音，只有光遇来源是 0%。
  结论：① 转换器没坏（同一脚本在 04_MIDI 里 82/83 都有低音）；② 是**源音域**决定的。
- 修法：整库 **降八度（transpose −12）** → C3–C5，完全落进原神音域且**零折叠零吸附**
  （连原来那个 C6 折叠也一起消失，比不降更干净），低音键占比 ~57%（每首中位 57%，蓝莲花 68%）。
- 代价：整首低一个八度。这是**音区选择**不是 bug —— 2 个八度的曲子只能占 3 个八度里的连续 2 个（低+中 或 中+高）。
  ⚠ 别自作主张改音高：**渲两版 mp3 让用户听后选**。

### 8.2b ⭐ 单曲「原琴演奏版」：分声部补低音（比整首降八度更优）
用户要的是「**某首歌的原琴演奏版**」= 占满 3 个八度、旋律不失真的可弹版。做法（案例《答案》）：
1. 源谱（光遇/官方）通常只在 **C4–B5** 活动 → 整个低音区（Z X C V B N M，C3–B3）空着。
2. **逐 onset 处理**：`len(group)==1` 的单音不管；和弦（≥2 音）里**保留最高音在原八度**，
   其余声部**整体下移 12**。
   - **零碰撞可证明**：下移的是「低于该刻最高音的音」，下移后最高也只到 D4，而保留的最高音 ≥E4；
     互不重叠、同键也不会撞 → 无需合并逻辑。
   - **零折叠零吸附**：和弦非最高音实测范围 C4–D5 → 下移后 C3–D4，全在 48–83 内。
3. 实测《答案》：724 音，下移 219 音（30.2%），低音键 **0 → 187（25.8%）**，音域 C4–B5 → **C3–B5（21 键全用到）**，
   密度/最大同按不变。
3.5 ⭐⭐ **三个必做细节（源是光遇 Sky 谱时全都会踩）**：
   a. **给下移的声部补足时值** —— Sky 谱的非顶声部全是 30ms（§8.1-7），直接下移 = 低音只有 3% 的时间在响、
      用户还是说「没低音」。规则：`end = min(start + 1200ms, 同键下一个音的开始)`，
      **按同键封顶** → 同键永不重叠（不会被合并吞掉击弦），同音重复也保住了每一次击弦。实测《江南》覆盖 3% → **94%**。
   b. **每个音头只下移「最低的那一个」和声声部**，别把非顶声部整组下移 —— 整组下移后低音区同时按 **7 键**（糊），
      只下移最低一个 → 最大同按 **4 键**、覆盖仍 94%。
   c. **验收指标是「低音覆盖时长占比」，不是「低音键有几种 / 低音音数」** —— 后者会骗人：
      实测同一份文件低音键 7/7、低音音数 355，但覆盖只有 3%（听不见）。报数就报覆盖占比。
4. **仍要渲 A（原八度）/B（整首 −12）/C（分声部）三版 mp3 让用户耳朵定** —— 结构干净 ≠ 好听。
⚠ 别做「分声部 **再**整体降八度」：会掉到 C2（<48），`convert` 会报警折叠 —— 这个 assert 就是防它的。
⚠ 顶声部 ≠ 永远是旋律（见 §6），所以这是**一组候选**里的一版，不是唯一答案。
- 工具：`tools/transpose_midijson.py` —— 每首过三道校验才写盘（键 ⊆ 21 键｜按下/抬起/按键数与原版逐一相等｜
  `verify_intervals` 偏差 ≤2ms）。实测整库 10,195 首：全 OK、偏差 0ms、25s 跑完。
- ⚠️ 坑：`midi_to_midijson.KEYMAP` 是 **音高 → 键字母**，所以 `set(KEYMAP.values())` 得到的是**键字母集**不是音高集
  （照抄 `sky_batch_migrate` 的 `KEYS = set(m2j.KEYMAP.values())` 会踩）；判「音高能否映射」要用 `KEYMAP.keys()`。
- ⚠️ 坑：`m2j.decode_events()` 返回 **`(时刻, 键字母, 是否按下)`** —— 键在**第 2** 个字段（写 `e[2]` 拿到的是 bool）；
  键 → 音高要自己翻 `REV = {v: k for k, v in m2j.KEYMAP.items()}`。
- ⚠️ 坑：`m2j.press_intervals()` 返回 **`{键字母: [(按下ms, 抬起ms), …]}`**（按**键**索引，不是按时刻）——
  要按时刻分组得 `sorted({d for v in iv.values() for d, u in v})`；把它当时刻字典用会直接 `'str' - 'str'` 报错。
- ⚠️ 「降半个八度」**不行**：移任何非 12 倍数都会让音名全乱（C 大调 7 个音里 5 个落到黑键）→ 只能吸附 → 音高被改。
  实测蓝莲花降 6 半音：80% 音落黑键、**36% 的旋律音程被改变**。合法移调只有整八度。

### 8.3 诊断「音调不对/很怪」—— 先查调性中心，不要猜
21 键只能弹**白键**，所以「无升号」本身不异常。真正的诊断量是**调性中心**：看**结尾音/和弦根音** + **低音出现频次 top4**。
- 正常：以 C 或 A 为中心（Always with Me 结尾 C4、卡农 G4、春日影 C5、aLIEz 低音 C3×609）。
- **异常：以 B 为中心**（B Locrian，现实中没人这么写）→ 几乎必然是「**B 大调源谱把每个升号向下吸附到白键**」的机器转换：
  主音 B 不变，其余音各降半音 → 整首变 B Locrian；除 B、E 外约 70%+ 的音都比原曲低半音。
  实例：官方 lemon（作者 `MidiTrans`，元数据全是占位符）结尾停在 B5、低音骨架 {F,D,B,G}；而 Lemon 原曲是 B 大调。
  同类指纹：以 D / F 为中心要警惕（也可能合法：D Dorian / F Lydian）。
- 元数据里的作者字段有用：`MidiTrans` 这类批量转换器的产物要重点查。
- **修复路径**（按推荐度）：① 换同曲的其它编排（先确认调性中心合理）；② **拿原调 MIDI + 整首移调到 C 大调**
  （B 大调 → +1 半音，音程完全保真；⚠ 若已占满 3 个八度，+1 会把顶端顶出音域需折叠）；
  ③ 度数旋转重建（C→D D→E…）—— 只能算近似，吸附已抹掉半音信息。

### 8.4 ⭐⭐ 会转调的歌（「连升两次调」这类）→ 按段移调改编
白键琴只有一个固定音阶，所以**整首照搬是不可能的**；能做的是**逐段整体移调**：
每段各自平移，使该段的用音全部落进白键，再用**音区高低**把转调效果还原。案例《九儿》（能弹！）：
1. **先测段界和段调，不要猜**（两道独立证据一起用）：
   - **自我对齐**：拿主旋律轨，搜 `(时间偏移 dt, 移调量 s)` 的最佳匹配 —— 同一段旋律的再现会
     跳出来（实测 0s 段在 93.0s 以 **+7 半音**再现、匹配 35/38 = 92%，直接坐实「升五度」）。
   - **特征音判别**（比「覆盖率最高的调」靠谱得多）：**覆盖率法会把 B 大调误判成 A 大调**
     —— B 大调去掉 D#/A# 后正好是 A 大调的子集，实测把段界算错、多出一堆多余吸附。
     用 `D自然/D#/A#` 的有无：`A# 多且无 D自然 → B 大调`；`D# 有且无 A# → E 大调`；`D自然 有且无 A# → A 大调`。
     实测得 A大调 0-40s → B大调 40-88s → E大调 88-133s（三段各约 45s，也对上了歌的「三遍」结构）。
2. **每段移调量**：把段主音搬到 0（C）的同余类里挑八度，目标是**该段音区落在 48–83 内**、
   且**后一段比前一段高**。案例：A 段 −9（→C，音区 55–76）、B 段 −11（→C，60–79）、
   E 段 −9（→**G 大调**，67–83，末段顶到琴顶 B5 —— 上升阶梯出来了）。
   要么全落 C 大调（零跑音但三段等高），要么允许后段落 G/D 大调换上升感（代价：该段 1–2 个
   音级要吸附）。**两条都做出来渲 mp3，让用户耳朵定。**
3. **多轨 GM MIDI 缩编成三层**：先靠「单音 onset 比例 + 音域 + 时长中位」认轨
   （实测《九儿》：主旋律 = 单音比 1.00 且音域高的那条；贝斯 = 最低那条；ch9 且音符时长中位
   40ms 的是鼓，必须排除）。每音头取「**琴键范围内**的最高 2 声部 + 全谱最低音（折进 C3–B3）」。
   ⚠⚠ **只从琴键范围内挑声部**：先挑再折叠会把低音陪奏折到中音区、把织体搅乱
   （实测折叠 55 处 → 改成先筛范围后 0 处）。⚠ 时值封顶 ~1.6s 才能把「最大同按」压到 5 键以内。
   ⚠⚠⚠ **别用「每音头取最高 N 个声部」定顶声部** —— 多轨里同音高的重复（两条弦乐轨同时奏 B5）
   会把 N 占满，真正的旋律声部反而被挤掉；更坑的是**长音铺底**（实测弦乐 B5 从 0.09s 按到 3.86s）
   比旋律的第一个音还高 —— 结果曲子一开始先响 1.8 秒的铺底长音，旋律晚进来，用户会直接来问
   「最开始怎么有个 W 的音」。**正解**：旋律**固定取主旋律轨**；第二声部只取**严格低于旋律**的音
   （实在没有就只留旋律+低音）。改完后同一段变成「旋律 + 低声部 + 低音」，铺底不再压过旋律。
   （另外两个「凭空多音」陷阱 —— 旋律拖长音时陪奏音被顶成旋律、没低音处造低音 —— 见下面第 7 条。）
4. **用户问「琴上没有的音，能不能用相邻两个键一起按代替？」→ 先讲清楚，再给方案**：
   不行。同时按 C+D 听到的是**两个音 + 拍频**（C4 261.6 / D4 293.7 差 ~32Hz），是「毛毛的」
   而不是中间的 C#；而且拨弦琴不能止音，那种毛躁会挂 1–2 秒。实测代价：最大同按从 6 键→**8 键**。
   但用户的直觉方向是对的 —— 正解是「**快速滑过**」：低邻居**轻点 → 落到高邻居**（实测 457 键、最大同按仍 6 键）。
   只用于**旋律/内声部**，低音的黑键音仍就近挪（低音做滑音只会糊）。
   ⭐ **间距是可调参数，两个约束卡着**：轻点时长 `t_grace` 与间距 `gap` 必须满足
   `30ms ≤ t_grace ≤ gap` —— ① 下限 30ms 是 BetterGI 的 `MIN_NOTE_MS`（再短不表达）；
   ② `t_grace ≤ gap` 是因为轻点必须**先抬起**再落下一个键，否则两键同响 = 又变回上面那个拍频毛刺。
   实测三档：`60/70`（初版）→ `35/45` → `30/30`（格式能表达的极限），**用户逐版听后选了 35/45**
   —— 再紧就听不出滑音、只剩主音前一点「沙」。改间距只动那十几处滑音（实测 23 处），
   其余数据一个字节不动 → 用 §0 的 `scripts/make_ab_excerpt.py` 剪受影响的那 10–30 秒做 A/B，别重渲整曲。
   ⚠ 别自己替用户定间距：这是听感，只能他耳朵定（他听完会说「感觉还可以」或再来一档）。
5. ⚠ **就近挪的方向是上下文决定的，别声称「一律往上」**：`snap(note, ctx)` 拿 ±1 秒邻域里哪个
   邻居白键出现得多就朝哪边。实测《九儿》47 个黑键音是 **31 上 / 16 下**（同一段里前面是 D4，
   那个 D# 就会往下挪成 D4）。对外报数前**对账一遍**：拿最终目标音回查该时刻是否真的响着。
   我曾对用户说「47 个全是往上挪」，被自己的复核推翻 —— 方向必须实测，不能按 code 的 tie-break 推。
6. 空白体检：统计 onset 间隔最大的几处，确认是不是源谱本来就空 —— 源谱有 3s 休止很正常，
   不要自己去补音。密度按 ♩ 速度折算：♩=62 的慢歌每声部 ~1 音/秒，三层 ≈ 3 音/秒 **是正常的**
   （§6 的 3.7–5.1 是按中速曲算的，别硬套）。
7. ⭐⭐ **缩编两个「凭空多音」陷阱（用户会逐秒报回来）**：
   a. **旋律在拖长音时，陪奏的新音会被当成新旋律**。只看「音头」的写法会漏掉：旋律从 19.84s 起拖一个
      2.4 秒的 G4，而钢琴轨在 20.32s / 21.29s 起的 B4 / D5 **比正在响的旋律还高** → 被顶上顶声部。
      用户听成「主旋律突然变成 B4、D5、又回来，不连贯」（原话：「19s『红满天』这块不是很连贯」）。
      **规则：先算「此刻正在响的最高旋律音」当**天花板**，新起的陪奏音不低于它就往下折八度（折不动才丢）。**
      修完这一段 = 旋律长音 G4 + 下方 B3/D4。
   b. **没有低音的地方别造低音**。「取全谱最低音折进 C3–B3」在源谱本来就只写中音（这一段最低音就是
      D5/B4）时会凭空多出一个低音。**只在真低音轨（贝斯/低弦轨，或钢琴轨里源音高 <55 的音）存在时才放低音。**
   两个都修完：《九儿》457 键 → 390 键、最大同按 6 → 4 键（更接近手弹），强校验仍 0.0ms。
   → 改完**只剪出问题那一小段**（10 秒）做三版对照（旧版 / 修好版 / 源 MIDI 原样，用 §0 的
   `scripts/make_ab_excerpt.py`）交用户耳朵，别把整曲重渲三遍。

8. ⭐⭐ **钢琴谱的长音 ≠ 琴能响那么久 → 只在「空白区」用「和弦重复」填掉（用户逐字指定的做法）**。
   实测源谱右手在 2:16.406 按下 C5+G5+C6 后**按住 3567ms**、左手按住 1692ms —— 钢琴能一直按着，
   **风物之诗琴拨响后 1~2 秒就衰减**，而源谱这几秒里没有任何新音头 → 照抄就是「没声音、和弦也没了」。
   用户对修法的原话（比我的版本更好，**照这个做**）：「**主旋律可以停，但是和弦可以不停，靠和弦的重复
   填充掉这些区域**……**只在空白区域填充，其他地方不要动**」。
   **规则**：
   a. **只处理空白区** —— 成品按下事件的相邻间隔 **> 1.5s** 处（余韵 ~1.5s，更短的间隔不算空）。
   b. ⚠⚠ **填的是「低音声部那一行的重复」，不是「把和弦同时按一遍」**（这是用户亲自纠正的版本，照这个做）。
      我第一版按「把空白开始时仍在响的和弦每 1.35s 重拨一次」做（几个音同刻再按下去），被否：
      用户原话「**不是让你填充一个同时按的音** …… 你应该看看这个空白处的**前面低音区这一行**，
      看看这里**重复的那一段和声，用这个低音声的重复填充**，**自然的衔接下一段**」。→ 正解：
      - 取空白起点前 **4 秒**内**低音区（≤B3）**的按下事件，算**中位间隔 = 源谱的低音脉冲**
        （实测 234ms = 八分音符，即你要接着走的节奏）；
      - 取**最后 6 个低音的音高**当「那一小节的音型」；
      - 从空白起点 **+1 个脉冲**开始，**按脉冲循环这个音型**往前铺，铺到下一个音头前（`b − 0.05`）为止；
        每个音只按 **~220ms**（低音声部本来就是短音，靠余韵连）。
      → 低音那条线像没停过、接进下一段，主旋律照旧停，**不新增任何「同刻多音」**。
   c. ⚠ 若补入的低音与「空白开始时仍在响」的同键长音相撞，`convert` 会把两段合并（补音就消失了）
      → 先把那个长音的尾巴截到补音前 40ms（原段不足 30ms 就跳过）。
   d. ⚠ **别给所有音一个固定按下时长**：固定值让前后音全部重叠，实测最大同按从 4 飙到 **9 键**（根本弹不了）。
      按下时长取 `min(1.125s, 该音的源时值)`。
   ⚠ **别做「全局长音补键」**：对**每一个**时值 >1.6s 的音都补（哪怕不产生空档），实测被用户判为
   「怎么里面有这么多莫名的重复的音」—— 补键只该出现在**听起来真的空掉**的地方。
   ⚠ **别用「拉长按下时长」来修** —— 承接 §4c：拨弦不能止音，按多久都一样，必须重新击键。
   实测效果（《天路》v7 低音型填充）：4 处空白（最长 3.05s）补入 40 个低音 → **>1.5s 空白 0 处**、
   总按键 978 → 1012、最大同按仍 4 键、**编辑区之外 965 个按键逐键与上一版完全一致**。
   可复制代码（含定位/填空/同键腾位置）、接口单位表与区外零改动的证明 → 
   `references/surgical-edit-on-landed-json.md`。
9. ⭐⭐ **钢琴右手的「八度重复音」不要两个都弹，旋律取低副本、内声部排除同音级**。
   ⭐ **先判定「哪条线是旋律」，别靠猜**（用户会反问「你能查查这里的主旋律是哪一段吗」）：
   把右手**每个音头的音高集合**分类统计 —— 实测《天路》192s：**单音 160 个**（= 没被加厚的纯旋律）、
   **2 音·八度重复 122 个**、**3 音·含八度重复 30 个** ⇒ **这份钢琴谱的右手 = 主旋律本身被加倍成八度**，
   不是三条独立声部。于是：**同一刻出现两次的那个音级 = 旋律**，多出来的第三音 = 内声部（不是旋律）。
   用户会先误判（实测「我误以为 E5 是主旋律，结果发现不是这样」）—— 上面的分类能一次说清，
   **别顺着他的猜测直接删音**：先把「谁是旋律」用数据答出来，再谈怎么改。
   ⭐ **旋律该放哪个八度：看「单音音头」的音区分布**（没被加厚的音头 = 直接告诉你旋律住哪）——
   实测 160 个单音音头里 **C5–B5 占 113 个**、C6–B6 只 36、C4–B4 10 个 ⇒ 旋律住 **C5–B5**。
   把旋律放到上八度副本（如 A5）就比它平常的位置高了一整八度，用户听成
   「**上面那个音挡住了主旋律 / 听起来有点多余**」（实测原话）。
   旧规则「取最高两个音」还会**把根音丢掉**（C5+G5+C6 只取 C6+G5）→ 只剩一个空心五度。
   **规则：旋律 = 该音头最高音级里取「低八度副本」（低于琴底才往上取）；内声部 = 右手里低于
   旋律最高副本、且与旋律**不同音级**的最高音。** 修完那一刻 = A3(低音)+A4(旋律)+E5(内声部)。
   《天路》全局效果：砍掉 122 个高八度重复音、补进 60 个延音键 → 978 → 973 键，密度 5.10 → 5.08。
   ⭐ **实操顺序（用户会点名具体位置，别自己全局铺开）**：
   a. 他说「1:56 处跟 E5 同时的 A5 多余，删掉就好」→ 修法是**直接删掉那个音**，
      不要自作主张用一个低八度副本去替（那是另一种改法，动到的音多很多）；
   b. 删之前**先扫全曲同模式并报数**：把「**同一刻同时按下了 X 和 Y**」的音头全列出来
      （实测《天路》= A5 与 E5 同刻共 **15 处**，其中 **14 处的源谱右手是同一种和弦** C5+G5+C6 —— 
      同一个音乐事件重复出现）。**只改他点名的那几处，把剩下 13 处的时刻列给他，问一句要不要一起改**；
      既不闷在被点名的两处（他会再来一轮），也不擅自动他未授权的那些音。
   c. 报数时给「模式全曲几处 / 其中几处同源」两个数 —— 他要的是「你知道全貌但听我的」。
10. ⭐ **自检报告里的「时长/空档」必须核对单位**。我曾在自检里写「最长空白 0.00s」并交了两版 ——
   真相是脚本把**秒当毫秒又除了一次 1000**（真实值 3.05s），是用户耳朵听出来的。
   凡在交付里报秒数，先拿一个已知定值反向验证（如全曲时长、某音头间隔）。

11. ⭐⭐ **「怎么有这么多莫名的重复音」→ 先量再归因：同键塌陷 ≠ 补键太密**。
   我的第一反应是怪自己新加的延音补键，量完发现**主要不是**：
   - **指标**：把成品的按下事件按音高分组，数「**同一个音在 1.6 秒内被连按 ≥2 次**」的处数，
     并按寄存器分 **低音带（≤B3）/ 中高音带** 两栏报。
   - 实测《天路》：没补键的 v1 就已有 **530 处、其中低音带 357 = 67%**；补键版 590（中高音 +51 才是我补的）；
     两条都修完 251（低音带 93）。
   - **根因**：左手琶音跨 2–3 个八度塞不进琴的一个八度低音带 → 同音级塌到同一个键（§4(b2)-4.5）。
     补键只占中高音带那一小块。**两个都要修，别只修一个。**
   - **修法两条，但别自己拍**：① 手术式 —— 只改他点名的位置（§8.4-9b），**保厚度**；
     ② 全局面 —— 低音 0.5s 分箱 + **同键不重复按**（让它当长音，交给和弦重拨维持）。
     实测全局面：按键 973 → 647、密度 5.08 → 3.39、最大同按 3、同音连按 590 → 251。
   - ⚠⚠ **全局面减薄会被退单**：用户听完直接说「**这一版没有之前那么厚了，请你回到最开始的那个完整版**」
     → 他重视的是**织体厚度**，不愿为了消重复而丢掉整个左手琶音。**顺序：先报归因 + 两种修法的代价，
     让他选；没点头不做全局减薄**（大减法 = 产品降级）。要给就给一个中间档（窗口 0.35s）。
   - ⚠ **别拿「密度高」解释重复**：同键塌陷在密度只有 3.4 音/秒时照样出现；密度只是症状之一。

## 9. 交付形态：合并成单一「完整曲库」
用户最终要的不是一堆中间目录，而是**一个能长期维护的曲库**：**只放 JSON，一首歌一份，且这份一定能弹**。
- **默认把全部 `.mid` 转成 midi-JSON，曲库内不留 `.mid"`** —— 用户实测 `.mid` 在 BetterGI 里弹不出来，JSON 才是同源格式。
  ⚠️ 别自作主张「保留没丢音的 `.mid` 以便留轨道筛选」—— 用户要的是能弹。
- 丢音的原件顶替出去，但 **原件不删**（留在 `scores/` 与全量备份 zip 里）；提供 `--keep-broken-midi / --adapt-all / --json-only` 开关。
- **曲库目录只放曲谱文件**（`.json`/`.mid`）：BetterGI 遍历目录下所有文件并尝试解析，塞 README/CSV 进去会产生告警。
- 子目录会被递归扫描（`RecurseSubdirectories = true`），按来源分子目录即可，只需挂**一个**父目录。
- **不要改原文件名**：BetterGI 逐曲设置按 `RelativePath` 存。但同名两版必须起可区分的**显示名**
  （JSON 显示 `name`、`.mid` 显示文件名）。官方文件有 `name` 残留模板值（实测「示例曲谱」出现在两首官谱上）→ 只改显示名。
- 清单 CSV 比自述可靠：写「曲名/文件名/目录/类型/来源/可演奏率/备注」并**校验清单与实际文件集合相等**；
  生成前先探目标文件是否被 Excel/解压器占用（Windows `PermissionError` 119），可退化为写 `_new`。

### 9.1 命名纪律（用户硬要求）
- **标题只用曲名** —— 不加任何产物信息（「21键适配」「原神适配」「转换版」），也不加归属标签。
- **`author` = `原作者 | Hermes 转换`**（例 `周杰伦 | Hermes 转换`）。原作者来源优先级：
  ① **源文件自带元数据**（光遇 Sky 谱 `author`/`transcribedBy`、MIDI 版权/序列名）；② **web_search 查证**
  （中文歌搜「《曲名》原唱」，日文歌搜「曲名 作曲 誰」命中率最高）；③ **查不到就只写 `Hermes 转换`，绝不猜**
  （同名曲太多：`rise`/`stay`/`Reason`/`雲雀`/`你看到的我`）。
  ⚠ 从文件名反推「A - B」谁是人谁是曲会错（实测有 `Deadman - 蔡徐坤` 这种反序）。
- **源文件名 / 转录者 / 音符统计 / 移调等细节全放 `description`**（BetterGI 列表不显示该字段）。
  ⚠ 源文件名常带 `_~{[#v1]}~_`、`（2）` 这类分叉标记，**一旦进 `author` 就会显示成「字符错乱」**（用户会截图来问）。
- 靠**目录**区分来源（`01_原琴JSON`=官方，`02/04/05`=我方）；官方条目 author 原样不动。
- 例外：同名多版本必须留限定词（`…（精简）`、`…（纯旋律）`），否则列表里重名没法分辨。
  同一首歌来自**两个来源**时：**新版加来源限定词**（如 `传奇（FF14版）`）两者并存；
  再**主动问一句要不要把「曲名」让给更好的那一版**（用户手里那份旧的可能还占着 `传奇` 这个名字）——
  别自己悄悄改名动他的条目。
- 实现：`merge_library.py` 里 `TAG = ""` + `strip_tag()` 幂等剥离旧标签（重跑即自动重命名，
  文件名与 JSON `name` 必须同时改）+ 标题空白规整（`re.sub(r"\s{2,}", " ", …)`）；
  重命名后查一遍**重名 0 + `name`/`author` 里无 `\ufffd`/`_~{`/双空格**。
- 清单 CSV 保留用户自建目录的行，但按 **(文件名, 目录)** 去重 —— 否则每重跑一次多两行。

### 9.2 补原作者（用户：「可以核对一下吗」）
- **映射表写进重建脚本**（`merge_library.py` 的 `ARTISTS` 字典，每行带 `# 依据`），不要只手改 JSON ——
  否则下次重跑合并就全被刷回 `Hermes 转换`。作者组装用 `author_for(name)`，查不到回退 `Hermes 转换`。
- **文件名带作者时先判方向**：`Beyond - 海阔天空` 是人在前，`Deadman - 蔡徐坤`、`春はゆく - Aimer` 是曲在前。
- **同名不同文件要分别建 key**（`奇迹再现` 与 `奇迹再现 - 游戏（原神）适配版` 是两个 key）。
- 产出 **`作者核对表.csv`**（曲名 | 原作者 | 实际写入 author | 依据/置信度）给用户复核，同时报「已填 N / 未定 M」。
- 动画/游戏 BGM 填**作曲者**（HOYO-MiX/陈致逸、ZUN、菅野祐悟、増田俊郎），不是演唱者；VOCALOID 填 **P 主**，不是「初音未来」。

### 9.3 曲库维护
- 用户自建目录（`05_我的新增/`）不能被重建脚本 `rmtree` 掉，清单里的用户行也要保留 —— 只重建脚本自己管理的子目录。
- 中间产物（旧曲库目录、旧打包）统一移进 `_archive/`，别让两个都能挂的曲库并存。
- ⚠️⚠️ **`merge_library.py` 必须带 `--json-only`**（本库就是用这个模式建的）：**无参数跑它会
  把 `04_MIDI-21键适配JSON/` 里 32 个 JSON 删掉、换成新建的 `03_MIDI原版/*.mid`**
  （默认模式保留原件、只适配丢音的），清单也随之从 04 行变 03 行 —— 实测踩过。
  跑到一半发现不对：`git checkout -- 完整曲库/04_MIDI-21键适配JSON reports/完整曲库清单.csv` 还原，
  再用 `shutil.rmtree` 删掉新建的 `03_MIDI原版/`（**别用 `git clean -fd`，会连未跟踪的新歌一起删**）。
  → 跑任何重建脚本前先确认 `git status` 干净，它就是你唯一的安全网。
- **换版纪律（用户听完选定新版后替换曲库条目）**：
  ① 旧版 JSON + 它的全曲 mp3 移进 `scores/<曲名>/` **留档**，文件名写**实际做法**（`_就近挪` / `_快速滑过`），
     不写 `_v3` / `上一版` 这类没信息量的名字；
  ② 曲库里**只放当前版**，覆盖同一个文件名（BetterGI 逐曲设置按 `RelativePath` 存，改名会丢设置）；
  ③ ⚠ **落库前把 description 里的「【对照版】/【试听版】」字样删掉** —— 对照件升级成当前版后带着这个前缀，
     以后自己看库会以为放的是试听件；
  ④ 落库后对账一次 `md5(落库 notes) == md5(构建产物 notes)` —— 证明落进去的就是你验过的那份，
     别看文件大小差不多就算过。
  ⑤ 整条版本链都要留在 `scores/<曲名>/`（每个中间版 JSON + 全曲/片段 mp3 + README 表格写清「当前版/旧版」），
     用户会明确说「换回上一版」；只留当前版 = 没法回退。
  ⑥ 换版落库后**主动问一句要不要提交** —— **本地 commit 直接做，push 到他的私有仓库要等他点头**。
     未提交的迭代 = 没有安全网（§9.3 前面那条 `git checkout` 还原就靠这个）。
  ⑦ **用户退单（「这版没之前厚了，回到最开始那版」）→ 从 `scores/<曲名>/` 的存档里
     逐字节拷回去**（拷完 `md5sum` 两份必须相等），并把清单行的描述改回该版 ——
     **别“重新生成一版看起来差不多的”**：重建会用新启发式重新选声部，他手里那份已认可的东西就变了。
     换回去之后，把该版已知的毛病列给他（他接着会按上面那种“点名式”让你改），你就从基线重新做手术。

## 10. 曲库规模与性能（上万首后 BetterGI 卡的原因）
根因**不是曲目多，是磁盘 I/O**。证据：
- `MusicLibraryService.ScanAsync()`：每次进页面枚举**全部**文件 → 逐文件 `ReadAllTextAsync` + `JObject.Parse`
  + 建完整时间轴（每首约 1,250 个事件对象）→ **无索引、无缓存，每次重做**。
- `FileSystemWatcher` 500ms 防抖：**目录里任何写入都会触发一次全量重扫**。
- 实测 10,195 个文件：冷读 **107s** / 热读 0.8s / JSON 解析 0.3s → **I/O 主导**（机械盘随机读 ~10.5ms/文件）。
- `CanParse()` 只认 `.json/.mid/.midi` → 改名 `xxx.json.off` 可「隐身」（全库留盘、只暴露热清单）。
- `ParseJsonAsync` 用 `JObject.Parse` → **一个文件只能一首歌**，不能合并成合辑减文件数。

**处置优先级**：① 挂载目录搬到 NVMe SSD（**不能只放 junction 指回机械盘**，读还是走机械盘）；
② 拆批次（500–1000 首/包）或只挂「精选」子集，用目录历史下拉切换；③ 扩展名隐身做热清单；④ JSON minify。
⚠ **别把含多个子目录的父目录挂上去** —— 会重复计算（实测 24,255 个文件）。

## 11.5 ⚠️ 其它乐器（余音/悠可琴 等带和弦排的）：单乐器弹不了、自动谱也踩坑

原神除了诗琴系列，还有**上排是和弦按钮**的乐器（如「余音」吉他、「悠可琴」）：
`Q W E R T Y U` = C / Dm / Em / F / G / Am / G7 七个和弦（按一下＝整组音同时响），
`A S D F G H J` 与 `Z X C V B N M` = 各一个八度白键音符（**共只有 2 个八度，比诗琴少 C5–B5 那一排**）。

- **BetterGI 的 10 个内置乐器模板（风物之诗琴/老旧的诗琴/镜花之琴/谐律键琴/跃律琴/悠可琴/晚风圆号/余音/绮筵之鼓/聚聚鼓）
  用的是同一套 `StandardMappings`（Z=48…U=83）**（源码 `GameTask/Music/Service/InstrumentProfileService.cs`）。
  → 给这类乐器用「含 Q–U 高音键」的谱，游戏里实际会**按到和弦按钮**；要按和弦排设计谱子，只能把 Q–U 当「和弦触发器」{Q=C, W=Dm, E=Em, R=F, T=G, Y=Am, U=G7}（BetterGI 一个键＝一个音，发得出键就出得了和弦）。
- **和弦表固定在 C 大调**，不能移调 → 只有 C 大调/自然小调的曲子用得顺；**含 V(大三)、III(大三) 等和弦的流行歌对不上**
  （实测《加州旅馆》B 小调 −2 到 A 小调后仍需 E、D、E7 三个和弦，表里没有）。
- 音域只有 2 个八度 → 前奏/间奏/solo 跨 3 个八度的曲子装不下。
- ⭐ **别被 B 站「余音吉他还原 XXX」的视频骗了**：实测 394 万播放的《加州旅馆》7 分钟版简介自述为
  「（**余音＋诗琴＋聚聚鼓**）超还原演奏」＋「为了最大还原原曲效果，**使用后期调音进行制作**」＋
  「键盘映射：**Bome's Midi Translator Classic、FL Studio 20**」——即**三件乐器合奏 + 后期修音 + DAW 驱动**，
  不是「单乐器 + 自动演奏谱」的效果。单乐器要还原吉他手感，仍然用诗琴 21 键（逐音弹出分解和弦＝指弹效果）。

### 11.5b ⭐ 余音自动谱的正确做法（实战教训，用户认可的比例是「每小节末尾一下」）

- **同时要旋律 + 和弦**：把旋律压进两个音符排（48–59 + 60–71），和弦留给第 3 排（72–83）。
- ⭐ **现成的 15 键光遇谱是最佳底**：光遇谱音域 C4–B5（60–83，全白键）→ **整体 −12 半音正好落进 48–71**，
  第 3 排自然空出来（14 个白键 = 2 个八度 = 音符排全宽，零吸附零折叠）。比从 MIDI 重编省事得多。
- ⭐ **和弦扫节奏：每小节末尾一下**（≈第 6 个八分）——**不要每拍/每 2 拍一下**：
  和弦是**长按型**，前一个还在响后一个就叠上来，实测「一直扫」被反馈「很不和谐」。
- ⭐⭐ **扫弦要跟主旋律走，不能盲打格子**（用户原话：「经常在主旋律空白间隔的地方莫名扫弦，和弦排布要基于主旋律」）。
  做法：先用现成的人声轨（或旋律走向）划出「主旋律在唱」的乐句区间 → **只在乐句内、且该时刻旋律在响时**落扫弦；
  乐句换气处、前奏、间奏/solo 一律不扫（前奏分解吉他、solo 本身就带和声，再扫就是双份/撞音）。
  定和弦时给顶声部（≈旋律线）×1.6 权重，并强制「和弦里含旋律当前音」。
  实测《加州旅馆》扫弦 182→107 下（完整版）/ 134→79（精简版），前奏与 solo 段扫弦数归零。
- ⭐ **和弦怎么定：别把上游 MIDI 的走向硬搬进和弦表**（B 小调 −2 到 A 小调仍需 E/D/E7，表里没有，
  只能 Em/Dm 顶替 → 用户听出「不和谐」）。改用**覆盖法**：取该时刻前 ~0.5s 谱里实际响着的音级（按时长加权），
  选「三音覆盖最多 − 缺音惩罚 + 与前一小节同和弦的惯性(+0.10)」的和弦 → 只强化谱里已有和声、不引入冲突音；
  实测每 2.0 小节换一次＝与原曲和声节奏一致。
- ⭐ **切分切在小节线，不要切在人声换气**。一个副歌常横跨 3 个换气句（《加州旅馆》副歌 ≈50s），
  按换气切会「刚进副歌就回主歌」。切之前先验上游谱与原曲时间轴是否 1:1：判据＝前奏是否整数个循环小节、
  总长是否＝各段之和（光遇谱拍格 202.5ms ＝ 148BPM 八分音符 202.7ms，两者同速；《加州旅馆》光遇谱
  前奏 32 小节＝两遍 16 小节循环、主歌 16、副歌 32，总 259.2s + 35.5s solo ＝ 294.7s，分毫不差）。
- 交付给**两版**：按段落精简（3–4 分钟）+ 一个音都不切的完整版（保底，切错还有退路）。
- 密度提醒：光遇谱自带 6.6 音/秒，加扫弦后 7.2–7.5 音/秒，高于 3.7–5.1 的理想区间 —— 用户嫌挤再抽内声部。

## 12. 本 skill 自带脚本的维护记录
- **2026-10-14 · `scan_midi_structure.py` tempo 崩溃（已修）**：`collect()` 收的 `tempos` 是拍长 µs 的
  **裸 int 列表**（不是 `(tick, µs)` 元组），第 87 行却写成 `tempos[0][1]` → `TypeError: 'int' object is not
  subscriptable`，整个脚本一进「① 全局」就崩，**调性和移调扫描表全拿不到**（而那是 §1.4 判「能不能上琴」的第一道闸）。
  同类里 `list_midi_gm_tracks.py` 存的是元组，所以它没崩 —— 两个脚本的 tempo 表结构**故意不一致，别照抄**。
  实测：修前 `九儿.mid` / `天路-2.mid` 双双崩溃，修后正常出全表（62.0 / 64.0 BPM）。
  排查心法：**看到「第一步/任何陌生 MIDI」这类脚本先拿一首真曲子空跑一遍**，别等到调性判错才发现工具本身坏的。

- **2026-10-15 · 新增 `verify_delivery.py`（成品交付前硬验收）**：把 §0.5 的四条 + §0.6 的结构检查
  固化成一条命令，输出 11 项指标并给 PASS/WARN/FAIL，任一 FAIL → 退出码 1（可做门禁）。
  包含：首音时刻、三排音区分布、按键数、每 10s 音符数、>2s 空档、同键最小间隔、
  `≥12 半音` 占比、最大同按、开头音名核对（`--expect-first-notes`）。
  **回归验证**：对已认可的茉莉花多层版 → 9 PASS / 0 FAIL；对已废弃的梁祝翻车版 →
  正确抓出「44.2 秒空白」与「开头 10 秒只有 3 个音」两个真问题。
  ⚠ **定标教训**：`≥12 半音` 占比这一项，单声部旋律阈值 ≤2%，但多层编曲（带琶音）天然 40–60%，
  一开始用单旋律阈值去卡已认可的多层成品，误报 57.3% FAIL —— 所以脚本默认走多层阈值，
  要卡单旋律得显式加 `--mono`。**任何阈值跨场景复用前，先用"已知正确样本"回归一遍。**
  依赖：无（只读成品 JSON，自带 21 键 KEYMAP 与 `decode_events`/`press_intervals` 复刻），
  不 import `midi_to_midijson`，可独立运行。日志里 `>` 号写进 f-string 时注意别嵌同类引号（踩过一次 SyntaxError）。
